### 0.2 本轮最值得记住的一条：`get_db_session` 是**依赖**，不是**工具函数**

本轮最大的时间黑洞不是某个语法错，而是**把 `Depends` 依赖当成了上下文管理器**：

```python
with get_db_session() as session:      # ❌ TypeError（实测：不支持 context manager 协议）
```

**它的正确用法只有一种——出现在路由形参里，写函数名，不写括号、不加 `with`：**

```python
SessionDep = Annotated[AsyncSession, Depends(get_db_session)]

async def login(payload: LoginReq, session: SessionDep):   # ✅ 框架调用它、框架负责收尾
    ...
```

| 场景 | 写法 | 谁负责收尾 |
|---|---|---|
| 框架注入（给 FastAPI 用） | `Depends(get_db_session)` | FastAPI |
| 自己要一个独立事务 | `async with SessionLocal()` | 我自己 |

**为什么这条值得单列**：它不报编译错。报错落在 `auth_repo.py`，但根因是
「**这段代码本来就不该出现在 `auth_repo.py`**」——`repository` 层是同步写法，
它不可能正确消费一个 async generator。全链路的四段断点见
`docs/代码审查-异步连接与Session规范.md` §11。

> 判断一个目录该不该改名，看的是**它有没有造成实际危害**。
> `database/` 只是名字不够精确（无害）；`/register` 前缀则会让客户端调错地址（有害）。
> 所以**优先修前缀，不动目录名**——这就是"最小必要收敛"。

**为什么要拆 config / Base / engine**（三条硬理由，审查文档 §6.2）：

1. **变化原因不同**：配置随**环境**变（改密码/开关）、命名约定随**建模规范**变、连接策略随**驱动/池化**变。三件事互不相关，塞一个文件 = 动任何一处都要改同一文件。
2. **依赖方向不能倒挂**：`Base` 是**模型层的基类**，被 `models/` 依赖；它绝不该反过来依赖「读配置、建引擎」。
3. **避免 import 副作用（最关键）**：Alembic 的 `env.py` 只要 `Base.metadata`，**不要 engine**。若 `Base` 和 `engine` 同文件，`import Base` 会顺带执行 `create_async_engine(...)` —— 一个纯元数据操作却建了连接池。拆开后 `import app.db.base` **零副作用**。

> ⚠️ **更正（2026-09-20，实测）**：本节早先写的「没有 `__init__.py` 会让 **Alembic 扫不到模型**」——**这个说法是错的**。
> 实测：`app/`、`app/model/`、`app/database/` 三处都没有 `__init__.py` 时，`import app.model.user` 照样把 `users` 登记进了 `Base.metadata`（`[]` → `['users']`）。
> **Alembic 从不扫描文件系统**，它只读 `env.py` 交给它的 `target_metadata`。所以 `__init__.py` 对 Alembic **不是必需的**。
> 真正必需的是 **`models/__init__.py` 这个「汇总 import 入口」**，理由见 §13.4-A。

## 4. Step 2 · `core/config.py` —— 为什么 `os.getenv` 不够

你现在的 `app/config.py`：

```python
import os, dotenv
dotenv.load_dotenv()
db_url = os.getenv("DB_URL")
```

**它有 4 个真实问题**（不是理论洁癖）：

1. **可能返回 `None`，且没人拦**。`.env` 没读到 / 键名拼错 / 部署忘了注入 —— 全部**静默返回 `None`**，一路传到 `create_async_engine(None)` 才爆炸，报的是：
   `AttributeError: 'NoneType' object has no attribute 'drivername'`
   你看到会去查 SQLAlchemy，其实根因是「配置压根没读进来」。
2. **全是字符串，布尔会出致命 bug**。一旦加 `DB_ECHO`：`os.getenv("DB_ECHO", "false")` 拿到的是字符串 `"false"`，而 `bool("false") == True` —— 你以为关了 echo，生产在狂打 SQL（含参数 → 违反 §7 日志脱敏）。
3. **散落各处，无单一事实源**：每个文件各自 `os.getenv`，键名写错没人提醒。
4. **密码会进日志**：`DB_URL` 含密码，一旦有人 `print` 配置对象就泄露。

**怎么写**：

```python
from pathlib import Path

from pydantic_settings import BaseSettings, SettingsConfigDict

BASE_DIR = Path(__file__).resolve().parents[2]   # 仓库根；注意是 parents（复数）


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=BASE_DIR / ".env",     # 绝对路径，见下方「为什么」
        env_file_encoding="utf-8",
        case_sensitive=False,           # 字段 db_url ↔ 环境变量 DB_URL
        extra="ignore",
    )

    db_url: str                          # 无默认值 = 必填，缺失启动即报错
    db_echo: bool = False                # 自动把 "false" 转成 False


settings = Settings()
```

> ⚠️ **是 `model_config`，不是 `config`。** 写成 `config = SettingsConfigDict(...)` 会直接报（实测 pydantic 2.13）：
>
> ```
> pydantic.errors.PydanticUserError: A non-annotated attribute was detected:
>   `config = {'env_file': '.env', 'env_file_encoding': 'utf-8'}`.
>   All model fields require a type annotation; if `config` is not meant to be a field, ...
> ```
>
> **为什么**：Pydantic v2 把「模型配置」的固定键名改成了 `model_config`。
> 你写 `config` 时，元类不认识这个保留名，就把它当成**一个普通的类属性**去解析；
> 而模型类里的属性必须有类型注解，于是报「检测到未注解的属性」。
>
> 这是 **v1 → v2 最常踩的坑**：v1 时代确实写 `class Config:`，肌肉记忆很容易带过来。
> 记住一句话：**v2 里 `Config` 类没了，只剩 `model_config` 这个字典**。

**为什么 `env_file` 要用绝对路径**：`env_file=".env"` 是相对**当前工作目录**的。用 IDE 或从别的目录起 uvicorn，`.env` 就找不到 → 必填校验失败。用 `Path(__file__)` 锚定，换目录也稳。

**为什么 `settings = Settings()` 写在模块顶层**：这正是「**启动即失败**」的来源——配置错在 import 那一刻就暴露，而不是等第一个请求进来才报晦涩错误。

**验收（别跳过）**：

```bash
.venv/Scripts/python.exe -c "from app.core.config import settings; print(settings.db_url); print(repr(settings.db_echo))"
# 预期：打印出 URL；db_echo 是 False，不是 'false'

# 故意让它失败：把 .env 里 DB_URL 改成 DB_URLX，重跑
# 预期：pydantic_core.ValidationError ... db_url / Field required
```

> 看到「**点名字段 + 启动就报**」就对了——这就是它相对 `os.getenv` 的全部价值。看完记得改回来。

### 4.1 如果 `Settings()` 真的报错，对号入座

> 实测环境：pydantic-settings 2.15 / pydantic 2.13 / Windows（2026-09-19）。

| 报错 | `env_file` 写法 | 运行目录 | 根因 | 解法 |
|---|---|---|---|---|
| `PydanticUserError: A non-annotated attribute was detected: config = {...}` | 任意 | 任意 | 用了 **v1 的键名** `config =`（或 `class Config:`），v2 不认 | 改成 `model_config = SettingsConfigDict(...)` |
| `ValidationError: db_url / Field required` | `".env"`（相对） | **不是**仓库根 | `env_file` 是相对**当前工作目录**解析的，找不到文件 | 改成 `BASE_DIR / ".env"`（绝对路径） |
| 同上 | 绝对路径 | 任意 | `.env` **不存在** | `cp .env.example .env` 并填好 `DB_URL` |
| 同上 | 绝对路径 | 任意 | `.env` 里**没有 `DB_URL`**（键名拼错 / 按上面「故意改坏」验证后忘改回） | 查键名：`sed 's/=.*/=<redacted>/' .env` |
| `ModuleNotFoundError: pydantic_settings` | — | — | 没装包 | `.venv/Scripts/python.exe -m pip install pydantic-settings` |

> ⚠️ 分清两类：**「`.env` 缺失 / `DB_URL` 缺失」是刻意设计的 fail-fast**，不是 bug；
> 只有「相对路径 + cwd 不对」和「没装包」才是真错误。
>
> 代价要讲清：**`.env` 不存在时 `import app.core.config` 会直接把进程带崩**。这是**有意为之**——
> 配置缺失应当立刻暴露，而不是等第一个请求才报 `NoneType has no attribute 'drivername'`。
> 但**部署时必须确认环境变量已注入**，否则服务起不来（12-factor：配置进环境，代码不留明文）。

**六种组合实测结果**（可复现）：

| `env_file` | cwd = 仓库根 | cwd = 别的目录 |
|---|---|---|
| `BASE_DIR / ".env"`（绝对，**本文推荐**） | ✅ OK | ✅ OK |
| `".env"`（相对） | ✅ OK | ❌ `ValidationError` |
| 指向不存在的文件 | ❌ `ValidationError` | ❌ `ValidationError` |
| `None`（只读真实环境变量） | ❌ `ValidationError` | ❌ `ValidationError` |

> 表里 ✅ 的前提是 `.env` 里确实有 `DB_URL`。**空参 `Settings()` 本身不是错**——
> 取值来源由 `model_config` 声明（环境变量天然支持；`.env` 要写了 `env_file` 才会读），
> 构造参数 `Settings(db_url=...)` 是留给「测试 / 临时脚本覆盖」用的，业务代码不写。

## 5. Step 3 · `core/security.py`

### 5.1 先讲思路（不然后面代码就只是背下来的）

**这个文件为什么存在**

不是「我们该有个安全工具类」，而是：

> 认证流程里有 **3 个动作，写错就是安全事故**，而且它们会被**多个地方**调用。
> 集中到一个文件，是为了让**危险的逻辑只有一个出处**——改一处全项目生效，审一处全项目放心。

如果不是这个理由，那这层就是没必要的抽象。

**为什么恰好是这 3 个函数：划分依据是「调用方」，不是「技术」**

按「技术上能做什么」划分，你会写出 `encrypt()` / `decrypt()`——但**bcrypt 根本没有解密**，
密码哈希是单向的，按技术划分直接走进死胡同。

正确做法是看**每个调用方需要什么**：

| 调用方 | 手上有什么 | 它要什么 | 于是需要 |
|---|---|---|---|
| 注册接口 | 明文密码 | 能存进库的东西 | `hash_password` |
| 登录接口 | 明文 + 库里的哈希 | 一个「对 / 不对」 | `verify_password` |
| 注册校验阶段 | 明文密码 | 「够不够强」 | `validate_password_policy` |

三个调用方、三种需求 → 三个函数。**没有第四个，因为还没有第四个调用方。**

**为什么「密码强度」放 `core/`，不放 `services/`（这是硬约束，不是口味）**

- 密码强度要在**请求校验阶段**就拦住（非法请求连 service 都不该进）→ **`schema` 必须调用它**
- 而 `schema` 的类型（`RegisterReq`）**要被 `services` import**
- 若策略写在 `services` 里：`schema → services → schema` = **循环依赖，import 直接崩**

所以它必须住在**任何层都能安全 import 的地方** → `core/`。
`core/` 在依赖图的最底层：**能引任何人，不被任何人引**。

### 5.2 代码

```python
import re

import bcrypt

from app.core.config import settings

_BCRYPT_MAX_BYTES = 72          # 见下方「为什么是 72」
BCRYPT_ROUNDS = 12

_HAS_LETTER = re.compile(r"[A-Za-z]")
_HAS_DIGIT = re.compile(r"\d")


def hash_password(plain: str) -> str:
    raw = plain.encode("utf-8")[:_BCRYPT_MAX_BYTES]
    return bcrypt.hashpw(raw, bcrypt.gensalt(rounds=BCRYPT_ROUNDS)).decode("ascii")


def verify_password(plain: str, password_hash: str) -> bool:
    try:
        return bcrypt.checkpw(
            plain.encode("utf-8")[:_BCRYPT_MAX_BYTES], password_hash.encode("ascii")
        )
    except (ValueError, TypeError):
        return False            # 哈希格式非法就当校验失败，不抛异常


def validate_password_policy(plain: str) -> str:
    if not (settings.password_min_length <= len(plain) <= settings.password_max_length):
        raise ValueError(f"密码长度需为 {settings.password_min_length}-{settings.password_max_length} 位")
    if not (_HAS_LETTER.search(plain) and _HAS_DIGIT.search(plain)):
        raise ValueError("密码需同时包含字母和数字")
    return plain
```

### 5.3 每个决策的理由（数据为本机 bcrypt 4.x / cost=12 实测）

**① 为什么不能「自己算哈希再比大小」—— bcrypt 自带随机盐**

```
同密码第一次: $2b$12$utq4ufSLf9RdV8i7iM9y2...
同密码第二次: $2b$12$Ofkicg3wuX4i3LwIAPFcH...
两次哈希相同吗？ False
```

同一个密码每次哈希都不同 → `hash(输入) == 库里的值` **恒为假**。
必须用 `checkpw`——它会从存好的哈希里读出 salt 重算。
**这就是 `verify_password` 存在的理由：把「必须成对使用的正确姿势」封起来。**

**② 为什么非封装不可 —— bcrypt 的 API 只吃 `bytes`**

```
bcrypt.checkpw(pwd, h1.decode())
→ TypeError: argument 'hashed_password': 'str' object cannot be converted to 'PyBytes'
```

数据库列是 `VARCHAR`（存 `str`），bcrypt 要 `bytes`；每次调用都要 encode/decode，忘一次就报错。
封装的价值 = **把容易传错的边界关进一个文件**，外面永远只见 `str`。

**③ 为什么不用 sha256 / md5 —— 它们是「快哈希」**

```
sha256  单次 0.67 微秒
bcrypt  单次 182 毫秒        → 慢约 27 万倍
爆破 100 万个密码： sha256 → 0.7 秒      bcrypt → 50 小时
```

sha256/md5 的设计目标就是**快**（用来校验文件完整性）。拿它存密码 = 给攻击者的 GPU 送加速器。
bcrypt 是**故意慢**的：你登录慢 182ms 无感，攻击者试 100 万次就得 50 小时。

**④ `cost` 怎么选 —— 每 +1 耗时翻倍**

| cost | 单次耗时 | 爆破 100 万密码 |
|---|---|---|
| 10 | 45 ms | 约 13 小时 |
| **12** | **185 ms** | **约 51 小时** |
| 14 | 736 ms | 约 205 小时 |

太低不安全；太高有 **DoS 风险**（攻击者拿登录接口刷，把你 CPU 打满）。
12 是安全与可用的平衡点，契约 §3.1 定 `>=12`。

**⑤ 为什么是 72 字节**

```
80 字节 → ValueError: password cannot be longer than 72 bytes, truncate manually if necessary
72 字节 → OK
```

bcrypt 4.x 对超长输入**直接抛错**（不是静默截断）→ 用户设个长密码就 500。
⚠️ **哈希与比对必须用同一个截断规则**，否则长密码永远验不过（hash 时截了 72、verify 时没截 → 比对失败）。

**⑥ 为什么 `verify_password` 吞异常 —— 但必须留痕**

哈希串被写坏时 `checkpw` 抛 `ValueError`，不该变成 500（信息泄露）；返回 `False` 走正常的「邮箱或密码错误」路径。
**但吞掉要留痕**，否则数据库被写坏了你完全不知道。比上面那版更稳：

```python
    except (ValueError, TypeError) as exc:
        logger.warning("密码哈希格式非法，已按校验失败处理: %s", exc)
        return False
```

**⑦ 为什么不用 passlib**

`passlib 1.7.4` 读不到 `bcrypt 4.x` 的 `__about__`，会告警甚至报错。直接用 `bcrypt` 更省事。

**⑧ 为什么策略抛 `ValueError`**

Pydantic 的 `field_validator` 会接住 `ValueError` → 转成校验失败 → 由 Step 4 的统一处理器变成 `400 / 40001`。
这是「**策略层只管报错，HTTP 层负责翻译**」的标准分工。

### 5.4 小结：代码的「形状」是推理的结果，不是拍脑袋

```python
_BCRYPT_MAX_BYTES = 72            # ⑤ 截断规则，只能有一个出处
BCRYPT_ROUNDS = 12                # ④ 成本，只能有一个出处

def hash_password(...)            # ② 封装 bytes/str 边界；对调用方只暴露 str
def verify_password(...)          # ① 正确比对姿势 + ⑥ 异常留痕
def validate_password_policy(...) # ③ 策略住 core，供 schema 调用（避免循环依赖）
```

每一项都能追溯到「**谁需要它**」和「**不这么做会出什么事**」。

## 6. Step 4 · `core/errors.py` —— 统一信封（✅ 已实测 · 2026-09-22）

### 6.0 设计思路：它不是「错误工具集」，是契约 §2.0 那个信封的**唯一出处**

契约 §2.0 规定响应体**永远**是这个形状 —— 成功和失败**共用同一个信封**：

```json
{ "code": 0, "message": "ok", "data": { } }
```

所以这个文件要管**两件事**，不是一件：

| 路径 | 现状（写这个文件之前） | 问题 |
|---|---|---|
| **成功** | `log_in.py` 里 `return {"message":"登录成功"}` | **没有 `code`、没有 `data`**，已和契约漂移 |
| **失败** | 全项目 4 处 `raise ValueError` | 进兜底 → **500 纯文本**，违反契约的 400/401/409 |

只做失败侧、不做成功侧，就会重演今天的局面：**错误统一了，成功各家手写**。

### 6.1 按「谁调用它」分成三组（不是按技术分层）

| 谁调用 | 要什么 | 为什么住这层 |
|---|---|---|
| **service / repo** | `BizError(code, message)` | 业务层不该 import fastapi、不该知道 HTTP 状态码 |
| **api 层成功路径** | `ok(data)` | 成功信封必须与失败信封**同源**，否则两处必然漂移 |
| **`main.py` 装配时** | `register_exception_handlers(app)` | 四个 handler 是信封的**消费者**，跟信封住一起才不会改一处漏一处 |

### 6.2 完整实例（逐条实测通过，见 §6.3）

```python
from enum import IntEnum
import logging

from fastapi import FastAPI, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from starlette.exceptions import HTTPException as StarletteHTTPException

logger = logging.getLogger(__name__)


# ① 码的「名字」：让 service 写 ErrorCode.EMAIL_TAKEN，而不是丢一个 40901 魔法数字
class ErrorCode(IntEnum):
    PARAM_INVALID   = 40001
    CAPTCHA_INVALID = 40002
    SESSION_INVALID = 40101
    CREDENTIALS     = 40102
    EMAIL_TAKEN     = 40901
    RATE_LIMITED    = 42901
    INTERNAL        = 50000


# ② 码 -> HTTP 状态码：契约 §2.0 的唯一出处，兼做「未登记码」的守卫
CODE_HTTP_STATUS: dict[int, int] = {
    40001: 400, 40002: 400,
    40101: 401, 40102: 401,
    40901: 409, 42901: 429,
    50000: 500,
}


# ③ 业务异常：service 只管「报什么错」，不知道 HTTP 是什么
class BizError(Exception):
    def __init__(self, code: int, message: str) -> None:
        if code not in CODE_HTTP_STATUS:
            raise ValueError(f"未登记的业务码：{code}")
        self.code = code
        self.message = message
        self.http_status = CODE_HTTP_STATUS[code]
        super().__init__(message)


# ④ 成功信封：返回 dict，让 FastAPI 继续走 response_model 序列化
def ok(data=None) -> dict:
    return {"code": 0, "message": "ok", "data": data}


# ⑤ 失败信封：返回 JSONResponse，因为 handler 的返回值会被直接当响应发出去
#    http_status 提成位置参数（不给默认值）：忘传会 TypeError，而不是静默返回 200
def envelope(code: int, message: str, http_status: int, data=None) -> JSONResponse:
    return JSONResponse(
        status_code=http_status,
        content={"code": code, "message": message, "data": data},
    )


# ⑥ 把框架的四条异常路径统一翻译成信封
def register_exception_handlers(app: FastAPI) -> None:

    @app.exception_handler(BizError)
    async def _h_biz(request: Request, exc: BizError) -> JSONResponse:
        return envelope(exc.code, exc.message, exc.http_status)

    @app.exception_handler(RequestValidationError)
    async def _h_validation(request: Request, exc: RequestValidationError) -> JSONResponse:
        errors = exc.errors()
        first = errors[0] if errors else {}
        field = ".".join(
            str(p) for p in first.get("loc", ()) if p not in ("body", "query", "path")
        ) or "request"
        detail = str(first.get("msg", "参数校验失败")).removeprefix("Value error, ")
        return envelope(ErrorCode.PARAM_INVALID, f"{field}: {detail}", 400)

    @app.exception_handler(StarletteHTTPException)
    async def _h_http(request: Request, exc: StarletteHTTPException) -> JSONResponse:
        code = ErrorCode.INTERNAL if exc.status_code == 500 else exc.status_code * 100 + 1
        return envelope(code, str(exc.detail), exc.status_code)

    @app.exception_handler(Exception)
    async def _h_unhandled(request: Request, exc: Exception) -> JSONResponse:
        logger.exception("未处理异常 %s %s", request.method, request.url.path)
        return envelope(ErrorCode.INTERNAL, "服务器内部错误", 500)
```

`main.py` 只需要两行：


### 6.4 逐决策理由（全部带实测）

**① 为什么用 `raise` 而不是 `return {"error": ...}`** —— 关键在**中断**。

注册流程是「查重 → 哈希 → insert」三步。若查重失败只 `return`，**后面两步照样执行** → 往库里插重复邮箱 / 撞唯一索引再炸一次。`raise` 是 Python 里唯一能「立刻停止当前函数并把控制权交给上层」的机制。

**② 为什么必须有 handler，不能「到处 raise 就够了」** —— 实测对比：

| 做法 | 结果 |
|---|---|
| 只 `raise BizError(40901, "邮箱已被注册")`，**不注册任何 handler** | **`500` + `Internal Server Error`（纯文本）**，`40901` 和 message **全部丢失** |
| 同一个 `raise`，注册了 handler | `409` + 完整信封 |

→ 没有 handler，精心写的 `BizError(...)` **退化成和 `raise ValueError` 一模一样**，写了等于白写。
准确说法：**能省的是「每个路由的 try/except」，不能省「handler 注册」**。

**③ 为什么 `envelope()` 必须返回 `JSONResponse`** —— 实测：handler 里 `return {"code": ...}`（dict）**不报错、不警告，静默降级成 `500` 纯文本**。框架拿到返回值后直接 `await response(scope, receive, send)` 当响应发出去，dict 没这个能力。
→ 这就是 `ok()` 返回 dict、`envelope()` 返回 JSONResponse 的**硬理由**：不是风格差异，是「能不能用」的差异。

**④ 为什么用显式表而不是 `http_status = code // 100`** —— 实测契约 7 个码**全部**满足 `http*100+n`（`40001//100=400` … `50000//100=500`），所以 `//100` 在现有码上 100% 成立。但反例：

```
20000 -> http_status=200   ← 一个「错误」返回 200，前端 res.ok 直接当成功，静默错
1001  -> http_status=10    ← 非法状态码
```

更关键：**只有显式表，`BizError.__init__` 里那句「未登记的码」校验才有意义**。用 `//100` 则任何 5 位数都能过，契约失去守卫。

**⑤ ⚠️ FastAPI 已经预装了三个 handler —— 你是「覆盖」，不是「注册」** —— 实测：只注册 `BizError` 一个，`app.exception_handlers` 里已经有 **4 条**。读 `fastapi/exception_handlers.py` 源码确认，预装的实现是：

```python
async def request_validation_exception_handler(request, exc):
    return JSONResponse(status_code=422, content={"detail": jsonable_encoder(exc.errors())})
async def http_exception_handler(request, exc):
    return JSONResponse({"detail": exc.detail}, status_code=exc.status_code)
```

→ 这两个就是「422 + `{"detail":[...]}`」和「`{"detail":"Not Found"}`」的来源。它们**写死了**格式，你没法用配置改，**必须自己覆盖**。

**⑥ `Exception` 的 handler 走的是另一条路** —— 读 `starlette/applications.py` L59-71：

```python
for key, value in self.exception_handlers.items():
    if key in (500, Exception):
        error_handler = value            # ← Exception 被单独拎出来
    else:
        exception_handlers[key] = value
middleware = (
    [Middleware(ServerErrorMiddleware, handler=error_handler)]        # 最外层
    + self.user_middleware
    + [Middleware(ExceptionMiddleware, handlers=exception_handlers)]  # 最内层
)
```

异常从内往外冒，先到 `ExceptionMiddleware`（沿 `type(exc).__mro__` 查表，查到就返回）；查不到才继续冒到最外层的 `ServerErrorMiddleware`。而后者处理完会 **re-raise** —— 这正是「`TestClient` 默认参数下异常穿透」的根源，**必须写 `TestClient(app, raise_server_exceptions=False)`** 才看得到 `50000` 信封。
好处是：**对外 50000 信封 / 对内保留完整堆栈**，两头都拿到（实测日志 2141 字符）。

**⑦ 为什么 `BizError` handler 不打日志** —— `40102`「邮箱或密码错误」是正常业务流，每天可能几千次，打 error 会刷屏、淹没真错误。只给兜底 handler 打。

**⑧ 为什么 `http_status` 是「查出来的」而不是 service 传的** —— service 里写 `ErrorCode.EMAIL_TAKEN` 就等于隐式决定了 HTTP 409，**但 service 代码里从头到尾看不到 `409` 这个数字**。这就是分层的意义。

**⑨ 为什么 `removeprefix("Value error, ")` 是必须的** —— 自定义 `ValueError` 在 Pydantic v2 里的 msg 前缀就是 `"Value error, "`，不去掉用户会看到机器话（实测：去掉后是 `password: 密码至少 6 位`）。

### 6.5 小结

| 约束 | 一句话 |
|---|---|
| `raise` 与 handler | **一对**，缺一不可。`raise` 产生信号，handler 翻译成 HTTP |
| handler 返回值 | **必须**是 Response 对象，返回 dict 会静默变 500 |
| 注册时机 | `app = FastAPI()` 之后即可，与 `include_router` 先后无关；**重复注册 = 覆盖** |
| 你能省的 | 每个路由的 `try/except` |
| 你不能省的 | `register_exception_handlers(app)` 这一次调用 |

**异步 session 必须回答三个问题**，缺一个都会出问题：

| 问题 | 答案 | 为什么 |
|---|---|---|
| 怎么拿到？ | `yield` 依赖 | FastAPI **只对 `yield` 依赖**在请求结束后执行清理；`return` 不行 |
| 谁来 commit？ | **service** | 读接口不该 commit；写接口自己决定事务边界。依赖里 commit 会让「只是查一下」也开事务 |
| 怎么收尾？ | `async with` 自动 close | 请求结束自动归还连接池，**不用手写 close** |

```python
async def get_session() -> AsyncGenerator[AsyncSession, None]:
    async with SessionLocal() as session:
        try:
            yield session
        except Exception:
            await session.rollback()      # 出异常必须回滚，否则脏事务留在连接池里
            raise
```

1. ✅ **`connect_args` 给 `create_async_engine`**——见上方 ⚠️。**已完成**
2. ✅ **`expire_on_commit=False`**——**已完成**。默认 `True` 时，`commit()` 后访问对象属性会触发**隐式 IO**，在异步里直接抛 `MissingGreenlet`。
3. ✅ **变量名不要叫 `AsyncSession`**——**已完成**（现为 `async_session_local`）。叫 `AsyncSession` 会与 SQLAlchemy 的类同名，之后没人分得清它指 sessionmaker 还是类；`dependence.py` 最初就是因此把类型注解写错。
4. ✅ **`try/except` 包住 `yield`**——**已完成**。注意 `try` 必须在 `yield` **之前**：异常是路由执行时**从 `yield` 那一点抛回来**的，只有包住它才接得住。

## 9. Step 7 · `schemas/` —— 为什么请求和响应必须两套模型

你现在的 `user_sche.py` 只有一个 `User_out`（还带着 `user_email` 这个内部命名）。

**必须拆成三件**：`RegisterReq`（入参）/ `LoginReq`（入参）/ `UserResp`（出参）。

```python
class RegisterReq(BaseModel):
    email: EmailStr
    password: str

    @field_validator("password")
    @classmethod
    def _check(cls, v: str) -> str:
        return validate_password_policy(v)          # ← 策略复用，不重复写规则


class LoginReq(BaseModel):
    email: EmailStr
    password: str            # ← 登录不做强度校验，那是注册的事


class UserResp(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    email: EmailStr
    created_at: datetime
```

**为什么响应模型绝不能复用请求模型**（这是最容易犯的错）：

请求模型**含 `password`**。如果拿它当 `response_model` 或直接返回，密码就会**原样回显给客户端**。
拆开之后 `UserResp` **物理上不存在** password 字段 —— 想泄露都泄露不了。
这比「记得别返回密码」这种靠人的自律可靠得多。

**为什么 `from_attributes=True`**：让 `UserResp.model_validate(user_orm_obj)` 能直接从 ORM 对象读属性。
**但注意**：service 对外应返回 Pydantic，**不要让 ORM 对象穿过层边界**（session 关闭后再访问属性会抛 `MissingGreenlet`）。

**为什么要做密码策略校验**（而不是在 service 里 `if`）：**在系统边界 fail fast**。非法请求连 service 都进不去，service 里就不用再操心「万一密码不合法」。

**为什么邮箱要 `EmailStr`**：`email-validator` 会自动做 RFC 校验 + 长度上限（≤254），不用自己写正则。

### 9.1 ⏸ 本轮约定：`schemas` 延后，但有一个风险必须守住

**决定**：本轮先不写 `schemas/`（`user_sche.py` 已被清空成只剩两行 import）。

**代价（要清楚自己在放弃什么）**：

1. **没有参数校验层** → 非法邮箱、弱密码不会被拦。契约里的 `400 / 40001` 就失去了来源。
2. **出参退回 `dict`** → 字段靠**手工白名单**枚举。
   ⚠️ 一旦写成 `vars(user)` / `user.__dict__`，`User` 上的 `password_hash` **会被原样带出去**。
   这正是 `UserResp` 的价值——它是**物理隔离**，不是靠人记得住。

**折中建议**：入参可以先用裸参数，但**至少落一个 `UserResp`**（只列 `id / email / created_at`，不含 `password_hash`）。
成本 5 行代码，换来"密码漏不出去"这个结构性保证。

```python
    try:
        await session.commit()
    except IntegrityError:                          # ← ③ 唯一索引兜底
        await session.rollback()
        raise BizError(40901, "邮箱已被注册") from None

    await session.refresh(user)                     # ← ④ 取回自增 id / 服务端默认
    return UserResp.model_validate(user)


async def login(session: AsyncSession, payload: LoginReq) -> UserResp:
    email = payload.email.strip().lower()
    user = await _get_active_user(session, email)

    # ⑤ 防用户枚举：账号不存在 与 密码错误 返回**完全相同**的错误
    if user is None or not verify_password(payload.password, user.password_hash):
        raise BizError(40102, "邮箱或密码错误")

    user.last_login_at = _utcnow()
    await session.commit()                          # ← ⑥ last_login_at 是写操作，必须 commit
    return UserResp.model_validate(user)
```

> `login` 复用 `UserResp`（含 `created_at`），比契约 §2.2 的 `{id, email}` 多一个字段——无害。
> 若你要严格对齐，另建一个 `UserBrief(id, email)` 即可。

**每一处为什么**：

① **为什么入库前 `lower().strip()`**：`A@B.com` 和 `a@b.com` 是同一个邮箱。不规范化，用户用大写注册、小写登录就登不上，而且能重复注册出两条记录。规范化和唯一索引**必须配套**——只规范化不建索引挡不住并发，只建索引不规范化会存两条「看起来不同」的记录。

② ③ **为什么既预检查又靠唯一索引**：预检查是为了给出**友好提示**（无法区分时只能统一报错，体验差）；但两个请求可能**同时**通过预检查，这时**唯一索引是唯一能兜住的**。少任何一个都有问题：只预检查 → 并发能插重复；只靠索引 → 提示不友好。

④ **为什么 `refresh`**：`id` 和 `created_at` 是数据库生成的，Python 侧还不知道，要读回来才能返回给客户端。

⑤ **为什么防枚举**（契约 §3.5）：如果「邮箱不存在」返回 `用户不存在`、「密码错」返回 `密码错误`，攻击者就能拿一个邮箱列表**逐个探测哪些邮箱注册过**。统一成一句「邮箱或密码错误」，两种失败**不可区分**。

⑥ **为什么 `login` 也要 `commit`**：`last_login_at` 是一次**真实的写操作**，不 commit 就等于没记。这也是「事务边界归 service」的直接体现——依赖层不管、路由层更不管，只有这一层知道「这次请求要不要落盘」。

> 原 ⑥ 是「为什么密码对了才说账号停用」。`status` 字段已删（§8.0），这条不复存在。**副产品**：错误码 `40101` 从「未登录 **或** 账号停用」两个语义收敛回一个（会话失效），语义更干净。

**为什么要 `await session.refresh` / `commit` 在 service 而不是依赖里**：见 Step 5 的「谁来 commit」。

### 10.1 本轮决定：**不加 repository 层**

`app/repository/` 是空目录——**本轮不建**。契约 §4.1 的分层是 `api → services → db/models`，**本来就没有 repository**。

**判断标准只有一句：这一层隐藏了什么复杂度？**

- 本轮 `users` 只有 1 个模型、2 个查询（按 email 查 + 插入）。包一层 repository，只是把 `select(...)` 从 service 挪到另一个文件——**复杂度没减少，只多了一个中转站**。
- 「所有 DB 操作都放 repo 层」这句话本身没错，**但它的前提在 SQLAlchemy 里不成立**：
  该说法多来自 Java/Spring——那边 `JpaRepository` 是**框架生成**的，你一行转发都不用写；
  SQLAlchemy 里仓储要**自己手写**，成本结构完全反过来，写出来就是纯转发：

  ```python
  async def get_by_email(session, email):
      return await session.scalar(select(User).where(User.email == email, ...))   # 函数体一行
  ```

**两个连带坑**：

1. **事务边界会碎**：repo 里一旦 `commit`，service 就**再也无法把多个操作合成一个事务**（例如以后注册要「插 `users` + 插 `user_profiles`」，必须同事务）。要写对，repo 只能「收 session、**绝不 commit**」——那它就更只剩一行 `select`。
2. **契约漂移**：§4.1 已写死分层，加一层属于**改架构**。按 `开发流程.md` §3 第②步（设计先行）+ §5（流程调整须先改文档），**应先改契约再动代码**。

**什么时候它真的值钱**（出现任一信号再抽，别提前造）：

- 同一查询被 **3+ 个 service** 复用
- 需要**多存储源**（如 MySQL + Redis 券/会话缓存）——这时 repo 能隐藏「先查缓存、miss 再查库、回填」的复杂度，**那才是真正的隐藏**
- 查询复杂到 service 被 join / 分页撑胖

> 另：**git 不跟踪空目录**。`app/repository/` 空着不会被提交，别人克隆下来根本没有 → 建议删掉，别让它悬着。

## 13. Step 11 · 建表（**本轮决定：直接上 Alembic，不用 `create_all`**）

### 13.1 为什么跳过 `create_all`

契约 §9.4 允许开发期用 `Base.metadata.create_all()`，但本轮**直接上 Alembic**：

1. `create_all` 只会「**建缺失的表**」，**不会改已有的表**。你改一个字段类型，它什么都不做——schema 与应用代码就悄悄漂移了。
2. `create_all` **没有版本记录**。表建出来了，但「这是第几版 schema」无从得知；一旦要回滚，没有任何依据。
3. `users` 表接下来**一定会改**（下一轮加 `user_sessions`、以后加索引）。第一次就用 Alembic，成本只多一个 `alembic init`；中途换，要处理「已有表但无版本基线」的破事。

### 13.2 职责三分：三个文件各管什么

| 文件 | 一句话职责 | 谁生成 |
|---|---|---|
| `alembic.ini` | **命令行怎么找到这套东西**（路径 / 日志 / 模板） | `alembic init` 生成，只改 1~2 行 |
| `alembic/env.py` | **一次迁移运行怎么起、怎么收**（取 URL、建 engine、交 metadata、事务边界） | 生成后**必须手改**，这是唯一需要动脑的文件 |
| `alembic/versions/*.py` | **这一次 schema 变化是什么**（`upgrade` / `downgrade`） | `--autogenerate` 产出 + **人工逐行审**。是产物，不是源码 |

**为什么 URL 不能写进 `alembic.ini`**（两条都踩过）：

1. **单一事实源**。URL 已经住在 `.env`，第二处 = 必然漂移（改库名忘了改另一个）。
2. **`alembic.ini` 会进 git**。写 URL = 把 `root` 密码写进版本库——`.env` 已经犯过一次入库的错（见审查文档 §10.2），不能再犯第二次。

### 13.3 为什么用 `-t async` 模板，而不是默认的 `generic`

- 项目 URL 是 `mysql+aiomysql://`。`generic` 模板建的是**同步** engine，**异步驱动喂不进去**，直接跑必炸。
- 替代方案是「再维护一个同步 URL」（`DB_URL` + `DB_URL_SYNC`）→ 又回到两个事实源；而且 `pymysql` **当前没装**（实测 `requirements.txt` 只有 `aiomysql`）。
- 官方 `async` 模板的做法：`env.py` 里用 `connection.run_sync()` 把异步连接桥接给 Alembic 的**同步**迁移 API。

> ⚠️ **最容易被误解的一点**：**应用运行时是异步的，迁移过程是同步的。**
> 用了 async 模板，**迁移脚本里仍然是普通的同步 `op.create_table(...)`**，不需要写 `async def upgrade()`。
> 异步只是 `env.py` 里薄薄一层桥。

### 13.4 动手前必须先搞清的一件事：`models/__init__.py`（**汇总 import 入口**）

> ⚠️ **先更正一个错误说法**：§1 早先写「没有 `__init__.py` → Alembic 扫不到模型」，**实测证明是错的**。
> Alembic **从不扫描文件系统**，它只读 `env.py` 递过去的 `target_metadata`。命名空间包（无 `__init__.py`）照样能 import、照样能登记表。
> **所以 `app/`、`app/core/`、`app/router/` 等目录的 `__init__.py` 是可选的**（写上更规范，不写也能跑）。

**但 `models/__init__.py` 是必需的**，而且理由和「Alembic 能不能找到」无关——它解决的是另一个问题：

#### 为什么必须有它：`Base.metadata` 是**空的开局**

`Base.metadata` 是那张「**有哪些表**」的清单。它**不是**自动生成的——**一开始是空的**。

只有当一个模型类被**真正执行过**（class 语句被执行），SQLAlchemy 才会把这张表登记进去。

> 📌 **关键心理模型：写了文件 ≠ 登记了表。**
> `app/models/user.py` 里写着 `class User(Base)`，只要**没有任何人 import 它**，这个 class 就永远没被执行，`Base.metadata` 里就永远没有 `users`。

实测（无 `__init__.py`）：
```
刚 import 完 Base          → Base.metadata.tables = []
再 import app.model.user   → Base.metadata.tables = ['users']
```

#### 所以要「汇总 import」，两种做法

**做法 A（笨的）：在 `env.py` 里把模型逐个列出来**
```python
from app.models.user import User
from app.models.order import Order          # 以后每加一个都要回来改这里
```
问题：**每加一个模型，都要跨越整个项目回来改 `alembic/env.py`**。忘了的后果是**静默的**——autogenerate 打印 `Detected no changes`，你以为建好了，其实那张表压根没进 metadata。

**做法 B（推荐）：建 `app/models/__init__.py` 作为唯一入口**
```python
# app/models/__init__.py
from app.models.user import User

__all__ = ["User"]
```
`env.py` 里永远只写一行：
```python
import app.models      # 这一行会执行 __init__.py，而 __init__.py 会 import 每个模型
```

**为什么 B 更好**：不是少打字，而是**把「需要被记住的事」放在离动作最近的地方**。
新增模型时你本来就在 `models/` 目录里干活，顺手补一行 `__init__.py`；而改 `alembic/env.py` 需要专门想起来、切换到另一个目录。

**并且 `env.py` 那里的注释要写清这一点**（见 §13.8 第 ② 段），否则下一个人删掉 `import app.models` 时，得到的是一句毫无线索的 `Detected no changes`。

#### 还差一步：`models/user.py` 的书写方式要先定下来

见 §13.5（本轮已按大宋拍板**放宽**：`INT` 主键、秒级精度都是**有意选择**）。字段清单见契约 §1.1。

### 13.5 类型怎么选：哪些是"口味"、哪些是"会坏"

> ⚠️ **本节 2026-09-21 重写**。上一版把「必须对齐契约的 3 处类型」写成了硬要求——**过度指定了**。
> 大宋拍板：**主键用 `INT`、时间用秒级 `DATETIME`、不写 `CHARSET/COLLATE`**（实测库默认已是 utf8mb4_0900_ai_ci）。
> 下面把"口味"和"会坏"分开，别再混为一谈。

**🟢 属于口味（怎么选都行，知道代价即可）**

| 选择 | 现状（大宋拍板） | 代价 / 升级路径 |
|---|---|---|
| 主键 `INT` vs `BIGINT UNSIGNED` | **`INT`** | 上限 21.4 亿；真要升是改列类型 = `INPLACE` |
| 时间精度 秒级 vs `DATETIME(3)` | **秒级** | 同秒内多条无法排序；升级 = `INPLACE` |
| 是否显式写 `ENGINE/CHARSET/COLLATE` | **不写** | 实测库 `price_agent` 就是 `utf8mb4 / utf8mb4_0900_ai_ci`，**表会继承 → 不写是对的**。只有换库到默认非 utf8mb4 的环境才需要显式声明 |

**🔴 属于"会坏"（跟口味无关，是功能缺失）**

| 写法 | 生成 | 后果 |
|---|---|---|
| `default=func.now()` | **DDL 里什么都不生成** | 实测编译结果是 `create_time DATETIME NOT NULL` —— **连 DEFAULT 子句都没有**。`default=` 是**应用侧**默认值，只塞进 SQLAlchemy 发出的 INSERT。**裸 SQL 插入 / 别的服务写入 → 这一列没有值 → `nullable=False` → 插入直接失败**。要用 `server_default=` |
| `last_login_time` 带 `default=func.now()` | 同上是 Python 侧 | **语义错**：新注册用户的"最后登录时间"会有值。应该让它 `NULL` |
| `String(100)` 给邮箱 | `VARCHAR(100)` | RFC 5321 允许 254。本机 `sql_mode` 含 **`STRICT_TRANS_TABLES`**（实测）→ 超长邮箱**直接报错**（不是静默截断）→ 注册 500 |

**自检办法**（不连库就能看到自己写出什么 DDL）：
```bash
.venv/Scripts/python.exe -c "from sqlalchemy.schema import CreateTable; from sqlalchemy.dialects import mysql; from app.models.user import User; print(CreateTable(User.__table__).compile(dialect=mysql.dialect()))"
```

### 13.6 两个真实的坑：`default` 不落 DDL，以及 `server_default` 的假 diff

**坑一（比类型重要得多）**：`default=` 与 `server_default=` 不是同义词。

| | 作用位置 | 出现在 DDL 里吗 | 谁会用不到 |
|---|---|---|---|
| `default=func.now()` | **应用侧**：塞进 SQLAlchemy 的 INSERT 语句 | ❌ 不会 | 裸 SQL、别的服务、DBA 手工插入 |
| `server_default=text("CURRENT_TIMESTAMP")` | **数据库侧**：写进 `DEFAULT` 子句 | ✅ 会 | 谁都能用上 |

对本项目的影响很具体：`create_time` 是 `NOT NULL`，一旦有人用 SQL 直接插一行，就会**报错**。

**坑二**：`server_default` 的文本写法会制造**恒久的假 diff**（实测 MySQL 8.0.46）：

| 写法 | 建表 | 第二次 `autogenerate` |
|---|---|---|
| `func.now()` / `text("now()")` | ✅ 通过 | ❌ 报 `modify_default` ——**每次都多一条无意义 ALTER** |
| `text("CURRENT_TIMESTAMP")` | ✅ 通过 | ✅ **无差异，干净** |

**根因**：MySQL 把 `now()` 规范化存成 `CURRENT_TIMESTAMP`，反射回来文本不同 → Alembic 认为默认值被改了。

> 顺带更正一个**我原本猜错的**：我以为 `DEFAULT now()` 会被 MySQL 当语法错拒绝，实测 `now()` / `CURRENT_TIMESTAMP` / `(now())` **多种写法全部通过**。
> 所以这是个「**能跑但不干净**」的坑——比语法错难查，你只会在每次 autogenerate 多出一条无意义 ALTER 时才隐约觉得不对。

**结论（秒级精度下的写法）**：
```python
create_time = mapped_column(DateTime, nullable=False,
                            server_default=text("CURRENT_TIMESTAMP"))
last_login_time = mapped_column(DateTime, nullable=True)      # 无默认值
```

**坑三（2026-09-21 实测发现，比前两个都隐蔽）：列默认值受「会话时区」影响**

`DEFAULT CURRENT_TIMESTAMP` 是按**当前连接的 session time_zone** 求值的，**它不是固定的 UTC**。
项目引擎在 `connect_args` 里钉了 `SET time_zone='+00:00'`，所以**只有走应用引擎的写入**才是 UTC。

实测（本地 17:45，UTC 09:45）：

| 写入方式 | session time_zone | `create_time` 实际存进去的值 |
|---|---|---|
| 项目引擎（`app.database.session`） | `+00:00` | **09:45** ✅ UTC |
| 裸引擎 / 命令行 / Workbench / 别的服务 | `SYSTEM` | **17:45** ❌ 本地时间 |

→ **同一列里会混着两种时区的时间**，而且每条数据看起来都"正常"，只是差 8 小时。
后果：按时间排序会错、「最近 N 天」的统计会漏/多算、两个时间列相减会得到 -8 小时。

**根治写法：用「表达式默认值」把时区钉死**（MySQL 8.0.13+ 支持）：

```python
create_time = mapped_column(DateTime, nullable=False,
                            server_default=text("(UTC_TIMESTAMP())"))   # ← 带括号！
```

实测**不受 session 时区影响**：在 `SYSTEM` 会话里插一行，得到的仍是 UTC `09:45` ✅。

> ⚠️ **括号不能随意**（实测三种，只有一种干净）：
> | metadata 写法 | 与库的往返比对 |
> |---|---|
> | `text("(UTC_TIMESTAMP())")` | ✅ **无差异** |
> | `text("utc_timestamp()")` | ❌ 报 `modify_default` 假 diff |
> | `func.utc_timestamp()` | ❌ 报 `modify_default` 假 diff |
>
> 根因：MySQL 存的是 `utc_timestamp()`、`EXTRA=DEFAULT_GENERATED`，`SHOW CREATE` 里带外层括号
> （`DEFAULT (utc_timestamp())`）——**只有带括号的文本才跟反射结果对得上**。
> 这与坑二同源：**默认值的比对是逐字符的，差一个括号就是永久噪音。**

> 🔴 **更硬的后果：不带括号连表都建不出来**（2026-09-21 实测 MySQL 8.0.46）：
> ```
> DEFAULT utc_timestamp()    -> ❌ (1064) You have an error in your SQL syntax
> DEFAULT (utc_timestamp())  -> ✅ 建表成功，插入得到 UTC 时间
> ```
> **MySQL 的「表达式默认值」必须带括号**（`DEFAULT (expr)`）。
> ⚠️ **这与 PostgreSQL 不同**——PG 里 `DEFAULT (expr)` 的括号可选，所以从 PG 转过来的人几乎必踩。
> 而 Alembic 是照着你 metadata 里的文本原样生成 `server_default` 的，
> 所以**模型里写 `text("UTC_TIMESTAMP()")` → 迁移里就是不带括号 → `upgrade head` 直接失败**。

### 13.8 `env.py` 全文（照着这段改；每段都有「为什么」）

`alembic init -t async` 生成的 `env.py` 有 89 行，**其中 3/4 原样保留**，只有下面标了 ①②③④ 的地方要改。
下面给的是**改完后的完整文件**，可以直接对照替换。


```python
"""Alembic 运行时环境。

职责：把「应用里的模型元数据」和「数据库里的真实结构」交给 Alembic 做对比。
这是配置脚手架，不走业务逻辑，不 import 任何 service / router。
"""
import asyncio
import sys
from logging.config import fileConfig
from pathlib import Path

from sqlalchemy import pool
from sqlalchemy.engine import Connection
from sqlalchemy.ext.asyncio import create_async_engine

from alembic import context

# ── ① 让 alembic 无论从哪个 cwd 被调用，都能 import 到 app/
#     必须放在 import app.* 之前——import 语句会在读到的那一行立刻执行
sys.path.insert(0, str(Path(__file__).resolve().parents[1]))

# ── ② 三样东西：配置、元数据容器、模型登记
from app.core.config import settings      # noqa: E402   URL 的唯一事实源（读 .env）
from app.database.base import Base        # noqa: E402   表清单的容器
import app.models                         # noqa: E402  ★触发所有模型登记★
#   ↑ 少了这一行：Base.metadata 是空的 → autogenerate 生成空迁移，
#     而且打印 "Detected no changes" 不报任何错。详见 §13.4。

# Alembic 的 Config 对象（读的就是 alembic.ini）
config = context.config

# 让 alembic.ini 里的 [logger_*] 配置生效
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

# ── ③ 交给 Alembic 的「期望状态」。它跟库里的「实际状态」做差集 = 迁移脚本内容
target_metadata = Base.metadata

# 对比开关显式写死，不吃 alembic 的版本默认值（否则升级依赖时行为会静默漂移）
_COMPARE_OPTS = {
    "compare_type": True,            # 列类型变了要报，如 VARCHAR(100) → VARCHAR(254)
    "compare_server_default": True,  # 默认值变了要报。注意 alembic 默认是 False！
}

def run_migrations_offline() -> None:
    """offline：不连库，只把 SQL 打出来（alembic upgrade head --sql）。

    给「DBA 审完 SQL 再手工执行」的场景用。
    """
    context.configure(
        url=settings.db_url,          # 模板这里是 config.get_main_option(...)，改成直连 settings
        target_metadata=target_metadata,
        literal_binds=True,           # 参数直接写进 SQL 文本，不占位
        dialect_opts={"paramstyle": "named"},
        **_COMPARE_OPTS,
    )
    with context.begin_transaction():
        context.run_migrations()

def do_run_migrations(connection: Connection) -> None:
    """真正干活的地方。注意 connection 是**同步**的。

    Alembic 整套迁移 API 都是同步的，异步驱动进不来；
    所以由 run_sync() 把我们带进同步上下文，这里才用得起来。
    """
    context.configure(
        connection=connection,
        target_metadata=target_metadata,
        **_COMPARE_OPTS,
    )
    with context.begin_transaction():
        context.run_migrations()

async def run_async_migrations() -> None:
    """online：连库执行。engine 自己建，URL 直接来自 settings。"""
    connectable = create_async_engine(
        settings.db_url,
        poolclass=pool.NullPool,      # 迁移是跑完就退的一次性进程，缓存连接没意义
    )

    async with connectable.connect() as connection:
        # ↓ 这就是「异步 → 同步」的唯一那层桥
        await connection.run_sync(do_run_migrations)

    await connectable.dispose()       # 显式关引擎，别把连接留着

def run_migrations_online() -> None:
    asyncio.run(run_async_migrations())

if context.is_offline_mode():         # 取决于命令行有没有加 --sql
    run_migrations_offline()
else:
    run_migrations_online()
```

**逐段为什么**：

| 段 | 改了什么 | 为什么 |
|---|---|---|
| ① | 加 `sys.path.insert` | Alembic 是命令行工具，不知道项目根在哪。你在项目根执行 `alembic ...` 时，`sys.path` 里其实**没有** `F:\price-agent`（脚本目录是 alembic 自己的）。不插这一行，`import app.*` 会 `ModuleNotFoundError`。`parents[1]` = env.py 的父目录的父目录 = 项目根 |
| ② | 换成 `import app.models` | 见 §13.4：**写了文件 ≠ 登记了表**。这一行才是真正让表进 metadata 的动作 |
| ③ | 加 `_COMPARE_OPTS` | 不写就吃 Alembic 版本默认值（1.12 起 `compare_type` 默认 `True`、`compare_server_default` 默认 **`False`**）。**升级 alembic 时行为会静默变化**——写死，行为就由你决定 |
| ④ | `create_async_engine(settings.db_url, ...)` 替代 `async_engine_from_config(...)` | 模板那条要从 ini 读 URL，而我们把 ini 的 URL 清空了（§13.2）。若改走 `config.set_main_option(...)` 注入，`ConfigParser` 会把 `%` 当插值符——**密码里带 `%` 就炸**。直接建 engine 既避开这个坑，又保证只有一个事实源 |

**为什么 `poolclass=pool.NullPool`**：迁移是跑完就退出的一次性进程。用连接池 = 跑完还攥着连接不放；DDL 也想要一条干净连接。

**为什么需要 `connection.run_sync(...)` 这层「桥」**（这是 async 模板唯一反直觉的一点）：
Alembic 内部用的是**同步** SQLAlchemy API，它不认识 `AsyncConnection`。`run_sync()` 把异步连接切进一个绿色线程，在那边当成同步连接用，跑完再切回来。
**所以：迁移脚本里你写的是普通的同步 `op.create_table(...)`，不是 `async def upgrade()`。** 异步只存在于 `env.py` 这一层。

### 13.8.1 配套的 `app/models/__init__.py`

```python
"""模型汇总入口 —— Alembic 的 env.py 只 import 这一个模块。

为什么需要这个文件：
    Base.metadata（那张「有哪些表」的清单）不是自动生成的，一开始是空的。
    只有模型类被真正「执行」过，SQLAlchemy 才会把表登记进去。

为什么汇总放在这里而不是写在 env.py：

    autogenerate 会打印 "Detected no changes"，你以为建好了，其实那张表根本没进去。
"""

__all__ = ["User"]
```

**`alembic check` 是什么**：它在**不生成文件**的前提下做一次 autogenerate 的对比，有差异就**非 0 退出**。
输出形如 `No new upgrade operations detected.` 就是干净。
（1.20 实测有这个子命令：`check   Check if revision command with autogenerate has...`）

**为什么要跑第 ③ 条**：它证明「**模型元数据与库已完全对齐**」。
若它报了内容，说明还有没对齐的地方——**趁现在改，比以后改便宜**。
⚠️ 注意：`check` 是否**默认**比较 `server_default` 取决于你的 `context.configure` 有没有开 `compare_server_default`（见 §13.8 ④）——我们已显式开启。

> 上一版这里建议的是 `alembic revision --autogenerate -m "noop check"` 然后看有没有输出、再删掉空文件。
> **有了 `check` 就别用那个土办法了**——它会真的生成一个文件、污染 `versions/` 目录。

## 16. 常见报错对照表

| 报错 | 根因 | 解法 |
|---|---|---|
| `ModuleNotFoundError: No module named 'app'` | 从错误的工作目录启动 | 在仓库根启动，或 `python -m uvicorn ...` |
| `AttributeError: 'NoneType' object has no attribute 'drivername'` | 配置没读到（`DB_URL` 缺失） | 上 pydantic-settings，看是否 `ValidationError` |
| `PydanticUserError: A non-annotated attribute was detected: config = {...}` | 用了 pydantic **v1** 的键名（`class Config` / `config = ...`） | v2 只有 `model_config = SettingsConfigDict(...)`；见 Step 2 |
| `TypeError: 'WindowsPath' object is not subscriptable` | 写了 `Path(__file__).resolve().parent[2]`——**单数** `parent` 返回的是一个 `Path`，不能再下标 | 用 **`.parents[2]`**（复数）：`parents` 才是可下标的祖先序列（`parents[0]` 是直接父目录） |
| `Can't connect to MySQL server` | MySQL 没起 / 账号密码错 / 用了 `localhost` 解析到 IPv6 | 先 `ping`/`netstat` 确认 3306；连接串用 `127.0.0.1` |
| `cryptography is required for sha256_password` | 缺 `cryptography` | 装它（MySQL 8 默认 `caching_sha2_password`） |
| `greenlet_spawn has not been called` / `MissingGreenlet` | session 已关闭还访问 ORM 属性 | `expire_on_commit=False`；关 session 前取完数据 |
| `MySQL server has gone away` | 空闲连接被服务端回收 | `pool_pre_ping=True` + `pool_recycle=3600` |
| 时间比预期差 8 小时 | MySQL `NOW()` 本地时间 vs Python UTC 混用 | 连接层 `SET time_zone='+00:00'`，全库统一 UTC |
| 建表报 `VARCHAR requires a length` | `Mapped[str]` 没给 `String(n)` | 每个字符串列都写长度 |
| 参数错误返回 **422** 而不是 `400/40001` | 没接管 `RequestValidationError` | 见 Step 4 |
| 接口全 404 | `main.py` 没 `include_router` | 挂上 `api_router` |
| `create_all()` 什么都没建 | 没 `import models` | 显式 import 触发注册 |
