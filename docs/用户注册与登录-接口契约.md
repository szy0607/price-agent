## 1. 数据库设计（MySQL 8，utf8mb4）

### 1.1 `users`

> ⚠️ **2026-09-21 修订（以代码为准）**：大宋拍板——**保留自己的命名**（`user_email` / `create_time` / `last_login_time`）、
> **加回 `username`**、**主键用 `INT` 不升 `BIGINT`**、**时间精度用秒级不升毫秒**、**`username` 不唯一**。
> 依据：项目约定「**契约可以灵活变通，但改动后果必须同步告知**」——**契约跟随代码，不反过来绑架代码**。

```sql
CREATE TABLE users (
  id              INT             NOT NULL AUTO_INCREMENT,
  user_email      VARCHAR(100)    NOT NULL                COMMENT '规范化后小写；登录凭据',
  username        VARCHAR(100)    NOT NULL                COMMENT '展示名，允许重名',
  password_hash   VARCHAR(255)    NOT NULL                COMMENT 'bcrypt/argon2，禁明文',
  create_time     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_login_time DATETIME        NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_users_email (user_email)
) ENGINE=InnoDB;
```

> **不写 `CHARSET` / `COLLATE` / `ENGINE` 之外的方言细节** —— 实测库 `price_agent` 建库时就是
> `DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci`，**表会继承，不用重复声明**。
> 这才是"灵活变通"该有的样子：**能不写就不写，前提是实测过默认值是对的**（本契约此前过度指定了，已删）。

要点：
- **只存哈希**，绝不存明文密码（红线）。
- `user_email` 入库前统一 `lower().strip()`；唯一索引兜底并发注册。
- **6 个字段就是全部**——没有 `nickname` / `status` / `updated_at` / `deleted_at`（见下 §1.1.1）。

#### 1.1.2 本轮"初步能跑"的宽松选择（**后果已实测，知情即可**）

| 选择 | 当前值 | 什么时候会咬你 | 到时怎么改 |
|---|---|---|---|
| 主键类型 | `INT` | 上限 **21.4 亿**，本项目基本撞不到 | 改列类型 = **`INPLACE`**（不重建表，但会动索引）。趁数据少时改便宜 |
| 时间精度 | `DATETIME`（**秒级**） | 同一秒内多条记录排序无法区分；并发写入的 `create_time` 会撞同一秒。**对注册/登录完全够用** | 加精度 = 改列类型 = `INPLACE` |
| `username` | **不唯一** | 允许重名 → **不能用它当登录凭据**（无法唯一定位人）。登录唯一键只能是 `user_email` | 想改唯一：`CREATE UNIQUE INDEX` = **`INPLACE`**，且存量重名要先清 |
| `user_email` 长度 | `VARCHAR(100)` | 🟡 RFC 5321 允许到 **254**。本机 `sql_mode` 含 **`STRICT_TRANS_TABLES`**（实测）→ 超长邮箱**不是静默截断、而是直接报错** → 注册会 500 | 改 254 = 改列类型 = `INPLACE` |

> **判据升级版（可复用）**：上一轮用「**时间点事件 vs 当前状态**」决定**要不要加这个字段**。
> 这一轮问题不同——字段已经有了，问的是「**给多大 / 多严**」。这时看的是：
> **改它要付什么代价**。走 `INSTANT` 的（加列）→ 随意；走 `INPLACE` 的（改类型 / 改索引）→ **能一次到位就别留尾巴**。
> 本轮这四项都是 `INPLACE`，所以**现在拍板、记进契约**，比以后改便宜。

#### 1.1.3 `username` 保留的两个注意点

| 注意点 | 说明 |
|---|---|
| **① 它不能当登录凭据** | 因为不唯一。登录唯一键是 `user_email`。**这条要在代码里写死**，否则以后一定有人写出 `WHERE username = ?` 然后拿错人 |
| **② 注册少了一条失败路径** | 只剩「邮箱冲突」一种 409 —— 比上一版更干净，**少一个用户枚举面**。这是"不加唯一约束"的额外收益 |

#### 1.1.1 字段取舍的判据（2026-09-20 修订）

原设计有 9 个字段，其中 4 个**没有需求来源**，已删除。删除依据是一条可复用的判据：

> **这个字段记的是「时间点事件」还是「当前状态」？**
>
> - **时间点事件** → 必须现在就有。**漏掉就永久丢失**，事后补只能得 `NULL`。
> - **当前状态** → 需要时再加。MySQL 8 加列走 `ALGORITHM=INSTANT`，**不重建表**（实测 2 行存量表瞬时完成，存量行自动回填默认值）。

| 字段 | 类型 | 判定 | 决定 |
|---|---|---|---|
| `id` `user_email` `password_hash` | — | 不成立功能就没有 | **保留** |
| `create_time` | 时间点事件 | 注册时刻补不回来 | **保留** |
| `last_login_time` | 时间点事件 | 登录历史补不回来；后续风控数据源 | **保留** |
| `username` | — | 2026-09-20 删过、**2026-09-21 加回**（大宋决定） | **保留**（后果见 §1.1.2） |
| ~~`nickname`~~ | 当前状态 | 无需求来源（惯例产物）；后补默认 `''` 语义正确 | **删** |
| ~~`updated_at`~~ | 行级变更时间 | **不是业务事件**，价值低；后补默认 `NULL` 也算对 | **删** |
| ~~`status`~~ | 当前状态 | 本轮无封号需求；后补默认 `1`（正常）语义正确 | **删** |
| ~~`deleted_at`~~ | 当前状态 | 本轮无注销需求；后补默认 `NULL`（未删）语义正确 | **删** |

> 📌 **命名口径**：本表字段名以**代码为准**（`user_email` / `create_time` / `last_login_time`），
> 不采用更常见的 `email` / `created_at` / `last_login_at`。**理由是大简单：代码已经这么写了，改命名要动 import 和已写好的查询。**
> **代价**：以后前端字段名、接口文档、日志字段都要跟着用这套名字，别混用两种风格。

**更正一处此前的错误说法**：本契约早先写「字段现在不加，以后要停机迁移」——**对加列而言不成立**。实测 MySQL 8.0.46，加列走 INSTANT、不重建表。真正有成本的是**加索引**和**改列类型**（两者为 INPLACE）。

**删除的连带影响**（施工时必须同步）：

| 被删字段 | 连带改动 |
|---|---|
| `nickname` | `RegisterReq` 少一个可选参数；`UserResp` 少一个字段；`register()` 少一个入参 |
| `status` | `login()` 里不再有「账号停用」分支 |
| `deleted_at` | **`_get_active_user()` 里的 `deleted_at IS NULL` 条件必须去掉**，否则 `AttributeError` |

**关于 PIPL 可删除权**：删掉 `deleted_at` **≠ 放弃红线⑥**（`开发流程.md` §7 第 6 条「用户可删除」），三点澄清：

1. **红线⑥的语境是用户画像**（对话中采集的预算 / 偏好 / 场景），不是账号本身——那批数据 M2 之后才有。
2. **实现「可删除」从来不靠这一列**。就算留着 `deleted_at`，只要没有「删除账号 / 删除画像」的接口，红线依然没落地；反过来，真删行 + 审计日志留存 userId 才是 PIPL 的正面做法——**软删严格说并不满足「删除」，因为数据还在库里**。
3. 本轮不提供注销接口，属于**已声明的有意偏差**（见 §7.1），不是遗漏。

将来做注销时，正确做法是**真删行 + 审计日志保留 userId**，而不是补一列 `deleted_at`（它属于"当前状态"，需要时 INSTANT 加回）。

### 1.2 `user_sessions`

```sql
CREATE TABLE user_sessions (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id    BIGINT UNSIGNED NOT NULL,
  token_hash CHAR(64)        NOT NULL   COMMENT 'session token 的 sha256(hex)',
  created_at DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  expires_at DATETIME(3)     NOT NULL,
  revoked_at DATETIME(3)     NULL,
  ip         VARCHAR(45)     NULL,
  user_agent VARCHAR(255)    NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_sess_token (token_hash),
  KEY idx_sess_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

要点：**Cookie 里放原始 token，库里只存 sha256**——即便库被拖，会话也不能被直接盗用。这样「登出 / 踢设备」= 删行或置 `revoked_at`。

## 2. 接口契约

### 2.0 统一约定

响应体固定信封：
```json
{ "code": 0, "message": "ok", "data": { } }
```
HTTP 状态码按语义返回，`code` 为业务码。错误码表：

| code | HTTP | 含义 |
|------|------|------|
| 0 | 200 / 201 | 成功 |
| 40001 | 400 | 参数校验失败（message 指明字段） |
| 40002 | 400 | 验证码错误或已过期 |
| 40101 | 401 | 未登录 / 会话失效 |
| 40102 | 401 | 邮箱或密码错误 |
| 40901 | 409 | 邮箱已被注册 |
| 42901 | 429 | 请求过于频繁 |
| 50000 | 500 | 服务器内部错误 |

### 2.1 注册

```
POST /api/v1/auth/register
```
请求：
```json
{ "email": "a@b.com", "password": "S3cret!pass" }
```
校验：`email` 合法且 ≤254；`password` 8–64 且含字母与数字。

响应 `201`：
```json
{ "code": 0, "message": "ok",
  "data": { "id": 1, "email": "a@b.com", "created_at": "2026-09-13T20:40:00+08:00" } }
```
错误：`409/40901` 邮箱已注册；`400/40001` 参数非法。
**响应体绝不包含 `password_hash`。**

### 2.2 登录

```
POST /api/v1/auth/login
```
请求：`{ "email": "a@b.com", "password": "S3cret!pass", "captcha_id": "b7c...", "captcha_code": "8F3K" }`

流程：**校验验证码**（见 §2.5）→ 查有效用户 → 校验密码 → 建 session → 下发 Cookie。

错误补充：`400/40002` 验证码错误或已过期；`429/42901` 触发限流。

响应 `200`：
```json
{ "code": 0, "message": "ok",
  "data": { "id": 1, "email": "a@b.com" } }
```
响应头：
```
Set-Cookie: session=<token>; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800
              （生产环境追加 Secure）
```
错误：`401/40102`——**统一提示"邮箱或密码错误"，不区分账号是否存在**（防用户枚举）。

### 2.3 当前用户

```
GET /api/v1/users/me        （依赖 Cookie）
```
响应 `200`：同 2.2 的 `data`。错误：`401/40101` 未登录或会话过期。

### 2.4 登出

```
POST /api/v1/auth/logout
```
流程：按 Cookie 定位 session → 置 `revoked_at`（或删行）→ 清 Cookie。
响应 `200`：`{ "code": 0, "message": "ok", "data": null }`

### 2.5 人机验证（验证码）

```
GET /api/v1/auth/captcha
```
响应 `200`：
```json
{ "code": 0, "message": "ok",
  "data": { "captcha_id": "b7c...", "image_base64": "data:image/png;base64,...", "expires_in": 300 } }
```
- 存 **Redis**：`captcha:{id} → code`，TTL 300s。
- 登录时携带 `captcha_id` + `captcha_code`；校验后**立即删除**（一次性），且**对错都作废**（防爆破）。
- 统一转大写比较；明文不进日志、不在响应回显。
- **分层防护**：限流（IP + email）→ 验证码 → 连续失败锁定。
- 完整设计与雷点见 `docs/登录人机验证与登录态-设计.md` §A。

## 3. 安全与合规自查（写代码前先过一遍）

1. 密码哈希：`bcrypt`（cost ≥ 12）或 `argon2id`；**禁** md5 / sha1 / 明文。
2. session token：`secrets.token_urlsafe(32)`（≥160 bit 随机）；库内只存 sha256。
3. Cookie：`HttpOnly` + `SameSite=Lax` + `Path=/`；生产 `Secure=true`。
4. CSRF：`SameSite=Lax` 挡掉大部分跨站 POST；状态变更接口再校验自定义头（如 `X-Requested-With`）或双提交 token。
5. 防枚举：注册/登录失败信息不泄露账号是否已存在。
6. 限流：登录/注册按 `IP + email` 限流（如 5 次 / 分钟）。
7. 日志脱敏：**不落**明文密码、session token；邮箱可脱敏为 `a***@b.com`。
8. PII 最小化：仅 `email + 时间戳`（红线⑥）。**不收集昵称、头像、手机号**——用不到就不收，这是 PIPL 最小必要原则的直接体现。
9. trace_id：中间件生成，响应头回传 `X-Trace-Id`，全链路日志带上（红线⑧）。
10. 命名：全文用「查询 / 采集 / 情报」，**禁用「爬取」字样**。

## 4. 目录结构（建议）

> 实际落地：本仓库把 `app/` 放在**仓库根**（与 `frontend-web/` 平级），未套一层 `backend/`。

```
backend/
├── app/
│   ├── main.py                       # FastAPI 入口 + 中间件（trace_id / CORS）
│   ├── core/
│   │   ├── config.py                 # pydantic-settings，读 .env
│   │   ├── security.py               # 哈希 / 校验 / token 生成
│   │   ├── logging.py                # 结构化日志
│   │   └── errors.py                 # 统一错误码 + 异常处理
│   ├── db/
│   │   ├── session.py                # engine / SessionLocal
│   │   └── base.py                   # DeclarativeBase
│   ├── models/                       # user.py, user_session.py
│   ├── schemas/                      # auth.py, user.py（Pydantic 契约）
│   ├── services/auth_service.py      # 业务逻辑（唯一性 / 哈希 / 会话）
│   ├── api/v1/                       # router.py, auth.py, users.py
│   └── deps.py                       # get_db / get_current_user
├── tests/                            # conftest.py, test_auth.py
├── alembic/                          # MySQL 迁移脚本
├── requirements.txt
└── .env.example
```

> 先写 `schemas/`（契约）→ 再写 `models` → 再写 `services` → 最后 `api`。**不要边写边想字段。**

### 4.1 依赖方向（铁律）

- 主链单向：`api → services → db/models`，**下层禁止 import 上层**（否则循环依赖必爆）。
- `schemas`（Pydantic 契约）被 `api` 与 `services` 共用；`services` 对外返回 dict / Pydantic，**不把 ORM 对象穿过层边界**（防 session 泄漏）。
- `core`（配置 / 安全 / 日志 / 异常）全层可用，但 `core` 自身不依赖任何业务模块。
- 所有 ORM 模型统一在 `app/models/__init__.py` 汇总 import，保证 Alembic 能发现全部表。

### 4.2 后续里程碑预留目录（现在不建，先留位置）

```
app/
├── agents/      # M1–M2  LangGraph A0~A5 状态图与节点
├── adapters/    # M5     联盟 API 统一适配层（Mock 与真实同签名）
└── rag/         # M3     检索增强：活动规则 / 券知识 / 规格库
```

### 4.3 命名约定

- 目录用复数（`models` / `schemas` / `services` / `api`）；文件用业务域名单数（`user.py`、`auth.py`）。
- ORM 类用单数名词（`User`、`UserSession`）；Pydantic 用后缀区分用途（`RegisterReq`、`UserResp`）。
- 一模块一文件；**禁止**把所有东西塞进 `main.py`。

## 7. 开工前决策（✅ 已全部拍板 · 2026-09-19）

| # | 决策点 | 结论 | 影响面 |
|---|---|---|---|
| 1 | MySQL 是否就绪 | ✅ 已就绪（本机 MySQL 8.0 运行中，见 §9） | — |
| 2 | 会话有效期 | **7 天 + 滑动续期**（`Max-Age=604800`；剩余不足 3 天才顺延） | 会话机制（下一轮） |
| 3 | 密码复杂度 | **≥8 位且含字母 + 数字**（不强制特殊字符） | 注册校验 + `core/security.py` |
| 4 | 是否本轮做邮箱激活 | **不做**（需邮件服务，留到后面） | 注册保持两步流程 |
| 5 | 前端联调时机 | **后端 `/me` 跑通后再做** | 本轮不碰 `frontend-web` |
| 6 | 本轮实现范围 | **只做注册 + 登录**；验证码 / 会话 / `/me` / 登出 / 限流 → 下一轮 | 见 §7.1 |
| 7 | 目录分层 | **沿用现有结构 + 最小必要收敛**（不整体重构到 §4 的 `db/ models/ api/v1/`） | 见 `docs/注册登录-实现指引.md` §1 |
| 8 | 是否加 repository 层 | **不加**（§4.1 的分层里本就没有；在 SQLAlchemy 下会退化成纯转发） | 见实现指引 §10.1 |
| 9 | `users` 字段取舍 | **只保留 5 个**（`id` `email` `password_hash` `created_at` `last_login_at`）；删 `nickname` / `status` / `updated_at` / `deleted_at` | §1.1.1（判据：时间点事件 vs 当前状态） |

### 7.1 本轮与契约的**有意偏差**（实现时知悉）

| 契约原文 | 本轮实际 | 原因 |
|---|---|---|
| §2.2 登录请求含 `captcha_id` / `captcha_code` | **不含** | 人机验证在下一轮；本轮 `LoginReq` 只有 `email` + `password` |
| §2.2 登录成功后 `Set-Cookie: session=...` | **不下发** | 会话机制在下一轮；本轮登录只返回用户信息 |
| §2.3 `GET /users/me`、§2.4 登出 | **不实现** | 下一轮 |
| §1.1 原设计含 `nickname` / `status` / `updated_at` / `deleted_at` 四列 | **不建这四列** | 无需求来源（见 §1.1.1）。MySQL 8 加列走 `ALGORITHM=INSTANT`、不重建表，将来真需要再加 |
| §2.2 登录响应含 `nickname` | **不含** | 同上 |

> 这些偏差是**增量的**，不是推翻契约：下一轮补上字段与接口后，本契约自动回到一致，**无需修改本文**。

### 7.2 补充：本轮新增的安全口径（原 §3 未覆盖）

| 项 | 口径 | 为什么 |
|---|---|---|
| **时间时区** | 全库统一 **UTC**（连接层 `SET time_zone='+00:00'`；Python 写朴素 UTC） | MySQL `DATETIME` 不带时区。若 `NOW()`（服务器本地）与 Python 写入混用会**差 8 小时**——实测：本地 17:06 时 `NOW()` 返回 09:06。ACTP 上已踩过此坑 |
| **密码字节上限** | 截断 **72 字节**（哈希与比对必须用**同一规则**） | bcrypt 只取前 72 字节，且 4.x 对超长输入**直接抛 `ValueError`** |
| **哈希成本** | bcrypt `cost=12` | 实测 ~185ms/次；爆破 100 万密码约 **51 小时**（同量级 sha256 只需 **0.7 秒**） |
| **参数校验失败返回码** | 必须**接管** `RequestValidationError` → `400 / 40001` | 否则 FastAPI 默认返回 **422** + 自带格式，与 §2.0 信封不符 |
| **响应体约束** | 出参模型**物理上不含** `password_hash` | 不靠"记得别返回"，靠**类型隔离** |
| **审计** | 每次请求带 `trace_id`，响应头回传 `X-Trace-Id` | 红线⑧ |

## 8. 数据库双库分工（MySQL + Milvus）

> 决策：业务库 = **MySQL 8**，向量库 = **Milvus**（替代设计稿 §5 的 `PostgreSQL + pgvector`）。

| 库 | 职责 | 存什么 | 里程碑 |
|----|------|--------|--------|
| **MySQL 8** | 业务 / 结构化数据（唯一事实源） | 用户、会话、对话、画像、推荐记录、审计日志 | 本轮起 |
| **Milvus** | 向量检索（RAG） | 活动规则 / 券知识 / 商品规格库的 embedding；**只存向量 + doc_id** | M3 |

关键约定：
1. **原文与向量分离**：知识原文（规则文本、券说明、规格）存 MySQL；Milvus 只存 `embedding + doc_id + 少量标量过滤字段`。检索命中后按 `doc_id` 回 MySQL 取原文。
2. **一致性**：知识更新时先写 MySQL、再 upsert Milvus（跨库，需补偿 / 重试，不做分布式事务）。
3. **embedding 维度**：建 collection 时锁定维度（与所选 embedding 模型一致，如 1024）；换模型必须重建 collection。
4. **部署**：开发用 Milvus Standalone（Docker Compose）；生产可上集群版。Windows 下 Milvus Lite 支持有限，优先 Docker。
5. **本轮无关**：用户注册 / 登录只碰 MySQL，不需要先装 Milvus；Milvus 到 M3 再接。

## 9. 开工顺序与本机环境

### 9.1 本机环境实测（2026-09-13）

- **MySQL 8.0 已安装且在运行**：`127.0.0.1:3306`（另 `33060` = X Protocol）；`root` 需密码（免密连接被拒 → 认证配置正常）。
- 命令行客户端：`C:\Program Files\MySQL\MySQL Server 8.0\bin\mysql.exe`（未加入 PATH）。
- 已装：MySQL Server / Workbench / Shell / Router 8.0；**未装 Docker**（M3 上 Milvus 时再装）。
- Python 3.13 可用。

### 9.2 推荐开工顺序（先基础设施、后业务）

> 原则：**基础设施先于业务**。数据库连接属基础设施（`core` + `db`），与业务契约正交；但业务侧仍必须 **契约 `schemas` 先于 `services`**。

1. **建库 + 建账号**（一次性 SQL，见 9.3）
2. `requirements.txt` + `.env` / `.env.example`（连接参数不进 git）
3. `app/core/config.py` —— pydantic-settings 读取 `DATABASE_URL`
4. `app/db/base.py`（DeclarativeBase）+ `app/db/session.py`（engine / SessionLocal / get_db）
5. **验证连接**：加一个 `GET /health`（内部 `SELECT 1`）或最小脚本，**确认连通后再往下写**
6. `app/models/` → Alembic 迁移建表 → `schemas` → `services` → `api`

### 9.3 建库建账号（MySQL，一次性执行）

```sql
CREATE DATABASE IF NOT EXISTS price_agent
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER IF NOT EXISTS 'price_agent'@'localhost' IDENTIFIED BY '<强密码>';
GRANT ALL PRIVILEGES ON price_agent.* TO 'price_agent'@'localhost';
FLUSH PRIVILEGES;
```
> 应用**不要用 root** 连库；开发也用专用账号，最小权限。

### 9.4 连接串与 MySQL 专属坑

- URL 格式（异步）：`mysql+aiomysql://price_agent:<密码>@127.0.0.1:3306/price_agent?charset=utf8mb4`
- 异步栈额外依赖：`aiomysql` + `greenlet`。**异步 session 获取规范见 `docs/代码审查-异步连接与Session规范.md`**。
- 依赖必须含 **`cryptography`**（MySQL 8 默认 `caching_sha2_password` 认证需要）。
- **连接池**：`create_engine(..., pool_pre_ping=True, pool_recycle=3600)` —— 否则空闲久了报 `MySQL server has gone away`。
- **时区**：MySQL `DATETIME` 不带时区。建议统一按 UTC 存，或连接时 `init_command="SET time_zone='+08:00'"`。**ACTP 上踩过"时间字段慢 8 小时"的坑，这里必须一开始就定死时区口径。**
- `echo=True` 只在开发开，生产关（避免刷屏 + 泄漏 SQL 参数）。
- 建表：开发初期可用 `Base.metadata.create_all()` 快速验证，**但正式表结构一律走 Alembic**，禁止线上 `create_all`。
