## 0. 先厘清一件事：这是哪个「卡片」

**项目里有两个都叫「卡片」的东西，别混**：

| | 购物车页面的「AI 补全」 | **本文的对话侧卡片** |
|---|---|---|
| 触发 | 在购物车页面点按钮 | **在对话里聊着聊着弹出来** |
| 形态 | 一个表单，字段填好了 | **一张卡片（图片 + 名字 + 参数）** |
| 结果 | 填进「添加商品」表单，你再提交 | **点卡片上的按钮入库** |
| 状态 | ✅ **已实现**（`POST /cart/items/ai-draft`） | ❌ **本文要设计的** |

**⚠️ 我曾经把这两个混为一谈**（2026-10-17），被大宋纠正过。
**共同点是复用 `spec_complete_service`，但触发方式、呈现形态、入库路径完全不同。**

## 3. 为什么是 SSE `card` 事件

三个选项对比：

| | 聊天气泡内嵌 | 独立消息类型 | **SSE `card` 事件** |
|---|---|---|---|
| 怎么传 | 塞进 assistant 文本里（要解析标记） | 落库为新 role | **SSE 帧，不落库** |
| 卡片内容 | 受 markdown 限制 | **需要落库**（违反「草稿不落库」） | **天然不落库** |
| 前端改动 | 解析 assistant 文本 | 新增消息渲染分支 | **新增事件分支** |
| 模型能看到吗 | ✅ 会污染上下文 | ✅ | **❌ 不进 messages** |

**🔴 关键理由**：`docs/流式输出-设计.md` §5.4 早就预留了这个位置——
「编排层需要能把 agent 事件透传到 SSE 生成器，这是编排层与传输层的新接缝」。
**现在 `rag_graph` 已经把接缝建好了**（TextSink + `_sse`），卡片直接复用。

**为什么不塞进 assistant 文本**：卡片是**结构化数据**（图片 URL、参数表、按钮），
塞进文本就要发明一套标记语法让前端解析——**那是把结构化问题退化成字符串问题**。

## 4. 卡片的按钮

| 按钮 | 动作 | 为什么有/没有 |
|---|---|---|
| **加入购物车** | 调 `POST /cart/items`（已有） | 唯一入库路径。**系统绝不自动入库**（合规红线） |
| **忽略** | 什么都不做 | 让用户能明确拒绝，避免下次又被弹 |
| ~~加入物品库~~ | ❌ 不做 | 「加入购物车」之后，用户可以再点「标记已购买」转物品库。**不要在卡片上多一个入口** |

**⚠️ 为什么不做「加入物品库」**：物品库 = 已购买。卡片里的是「候选商品」，
还没买——**卡片上出现「加入物品库」会让用户误以为这是已购记录**。

## 5. 技术实现

### 5.1 流程

```
用户：「想买个降噪耳机送人」
  ↓
decide 节点：模型决定调 complete_specs 工具
  ↓
card 节点：
  ① 调 spec_complete_service.complete_specs（复用现成的）
  ② 组装成卡片 payload
  ③ sink.write_card(payload)   ← 新方法，TextSink 要加
  ④ 返回一个「已展示卡片」的 tool 结果给模型
  ↓
模型：基于参数回答（「索尼 WH-1000XM5 是个不错的选择，续航 30 小时…」）
  ↓
前端：收到 card 事件 → 渲染卡片；收到 delta → 渲染回答
```

### 5.2 `TextSink` 要加一个方法

```python
class TextSink:
    def __init__(self):
        self._pending: list[str] = []
        self._cards: list[dict] = []

    def write(self, chunk: str) -> None: ...      # 现有

    def write_card(self, card: dict) -> None:     # 🔴 新增
        self._cards.append(card)

    async def flush(self) -> list[str]: ...       # 现有
    async def flush_cards(self) -> list[dict]:    # 🔴 新增
        ...
```

**🔴 为什么卡片要单独一个队列**：文本是「增量追加」，卡片是「一次性完整的结构」。
混在一个列表里，前端得靠类型字段区分每个片段——**但 flush 是按「块」切的，
一块里可能既有文本又有卡片**。分开更清楚。

### 5.3 SSE 帧

```
event: card
data: {"draft": {"name":"索尼 WH-1000XM5","category":"耳机",
                 "price":2299,"specs":{"品牌":"索尼","续航":"30小时"},
                 "model":"qwen-max","sources":["https://..."]}}
```

**🔴 `sources` 只用于展示「来源：网络」，绝不能原样渲染成可点击链接**——
博查返回的 URL 可能带返佣（CPS），项目铁律明令禁止。

### 5.4 前端渲染

```vue
<!-- 一行可展开，与 tool_calls 同一个位置 -->
<div v-if="message.card" class="mb-2 rounded-lg border border-zinc-200 p-3">
  <p class="text-sm font-medium">{{ message.card.name }}</p>
  <p v-if="message.card.price" class="mt-0.5 text-xs text-zinc-500">¥{{ message.card.price }}</p>
  <p class="mt-1.5 text-xs text-zinc-500">
    <span v-for="(v, k) in message.card.specs" :key="k">{{ k }}：{{ v }}</span>
  </p>
  <p class="mt-1 text-[10px] text-zinc-400">来源：网络 · 参数仅供参考</p>
  <div class="mt-2 flex gap-2">
    <button @click="addToCart(message.card)">加入购物车</button>
    <button @click="dismiss(message.id)">忽略</button>
  </div>
</div>
```

**⚠️ 卡片本身要不要落库**：**不落**。它是「这一轮的检索快照」，
和 `index_status` 一样是瞬时状态。落库的是**用户点确认后调 `POST /cart/items` 的结果**。

## 6. 🔴 与 RAG 工具化的关键区别

| | RAG 的 `search_my_items` | 卡片的 `complete_specs` |
|---|---|---|
| 搜什么 | **用户自己的物品** | **联网找外部商品** |
| 要钱吗 | ❌ 只调 embedding（用户的 key） | ✅ **1 次博查 ~0.036 元** |
| 慢不慢 | ~300ms | **数秒**（博查 + 主模型） |
| 有副作用吗 | ❌ 纯读 | ⚠️ **会展示一个待入库的草稿** |
| 该不该限制次数 | 不必 | **应该**（花钱） |

**🔴 所以卡片工具需要限次，而 RAG 不用。**
建议复用 A5 的限次机制（`A4对比与A5推荐-设计.md` §3.4），
或者用**同一个 Redis 计数器**——用户一天能触发多少次「花钱的 AI 功能」应该有总账。
