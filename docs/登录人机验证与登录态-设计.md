## A. 人机验证（验证码）

### A.1 方案对比

| 方案 | 抗破解 | 成本 | 合规 | 适合 |
|------|--------|------|------|------|
| 自研图形字符码（Pillow） | 低（易被 OCR 破解） | 0 | ✅ | Demo / 起步 |
| 滑块 · 行为验证（腾讯验证码 / 极验） | 高 | 有免费额度 | ✅ 国内厂商，数据不出境 | 正式产品 |
| reCAPTCHA / hCaptcha | 高 | 免费 | ⚠️ 数据出境 + 国内网络不稳 | 不推荐国内产品 |
| 无感风控（不弹码，靠行为评分） | 中高 | 需数据积累 | ✅ | 后期优化 |

> 现实提醒：你们在 ACTP 项目里已经用 cnocr 破过若依的图形验证码 —— 自研图形码强度确实有限。所以**验证码不要当唯一防线**。

### A.2 推荐：分层防护（而不是只加一个验证码）

1. **第 1 层 · 限流**：按 `IP + email` 限流（如 5 次 / 分钟，Redis 计数）—— 挡掉绝大部分脚本。
2. **第 2 层 · 验证码**：连续失败 N 次后（或每次）要求验证码；Demo 用自研图形码，正式换腾讯 / 极验滑块。
3. **第 3 层 · 锁定**：同一账号连续失败 M 次 → 临时锁定（如 15 分钟）。

### A.3 接口契约（自研图形码版）

```
GET /api/v1/auth/captcha
→ 200 { "code": 0, "message": "ok",
        "data": { "captcha_id": "b7c...", "image_base64": "data:image/png;base64,...", "expires_in": 300 } }
```

登录请求增加两个字段：
```json
{ "email": "a@b.com", "password": "S3cret!pass", "captcha_id": "b7c...", "captcha_code": "8F3K" }
```

新增错误码 `40002`（HTTP 400）：验证码错误或已过期。

### A.4 存储与校验要点（关键）

- 存 **Redis**：`SET captcha:{captcha_id} = {code} EX 300`（5 分钟 TTL）。
- **一次性**：校验时"先读后立即删除"（`GETDEL`）—— 防同一 id 反复试。
- **失败也删**：不论对错都作废，强制刷新验证码（防爆破）。
- **大小写**：统一转大写比较，减少用户挫败。
- **不落日志、不回显**：验证码明文不进日志、不在响应返回。
- `/captcha` 无需登录即可调用，但**要加限流**（防拿验证码接口被刷）。
- `captcha_id` 用 `secrets.token_urlsafe(16)`。

### A.5 雷点

1. **多 worker 下别用内存字典**存验证码 —— 进程间不共享，校验必然失败。用 Redis（已在跑）。
2. 别把答案编码进 `captcha_id`（可预测 / 可解），必须服务端存储。
3. 前端把 base64 直接塞 `<img src="data:image/png;base64,...">`，点击刷新即重新 `GET /captcha`。
4. Redis 异步客户端用 **`redis.asyncio`**，别用已废弃的 `aioredis`。

## B. 登录态维持（Session Cookie）

### B.1 生命周期（四环节）

见对话中的流程图：

1. **登录成功 → 发会话**：生成随机 `token`（给浏览器），库里只存 `sha256(token)`（给数据库），`Set-Cookie`。
2. **后续请求 → 校验**：浏览器自动带 Cookie → 依赖查 `user_sessions` 有效则放行，否则 `401/40101`。
3. **临近过期 → 滑动续期**：延长 `expires_at` 并重发 Cookie（节流：剩余不足 3 天才续）。
4. **登出 / 踢设备 → 失效**：置 `revoked_at` + 清 Cookie；改密 / 全端登出 = 按 `user_id` 批量失效。

### B.2 登录成功：发会话

```python
import hashlib
import secrets
from datetime import datetime, timedelta, timezone

token = secrets.token_urlsafe(32)                        # 给浏览器
token_hash = hashlib.sha256(token.encode()).hexdigest()  # 给数据库
expires_at = datetime.now(timezone.utc) + timedelta(days=7)

session.add(UserSession(
    user_id=user.id,
    token_hash=token_hash,
    expires_at=expires_at,
    ip=request.client.host,
    user_agent=request.headers.get("user-agent", "")[:255],
))
await session.commit()

response.set_cookie(
    key="session",
    value=token,
    httponly=True,
    samesite="lax",
    secure=settings.cookie_secure,      # 生产 True
    max_age=7 * 24 * 3600,
    path="/",
)
```

> **会话固定防护**：登录成功后**新发一个会话**，绝不复用登录前的任何标识 —— 标准做法。

### B.3 每次请求：校验依赖

```python
from fastapi import Cookie, Depends


async def get_current_user(
    session: SessionDep,
    session_token: str | None = Cookie(default=None, alias="session"),
) -> User:
    if not session_token:
        raise AuthError(40101, "未登录")

    token_hash = hashlib.sha256(session_token.encode()).hexdigest()
    row = await session.scalar(
        select(UserSession).where(
            UserSession.token_hash == token_hash,
            UserSession.revoked_at.is_(None),
            UserSession.expires_at > datetime.now(timezone.utc),
        )
    )
    if row is None:
        raise AuthError(40101, "会话失效，请重新登录")

    user = await session.get(User, row.user_id)
    if user is None or user.status != 1 or user.deleted_at is not None:
        raise AuthError(40101, "账号不可用")
    return user
```

### B.4 持续 / 续期：滑动过期（sliding expiration）

- **纯固定 7 天**：简单，但第 7 天必然被踢，体验差。
- **滑动续期（推荐）**：校验通过后，若 `expires_at - now < 3 天`，则把 `expires_at` 顺延为 `now + 7 天`，并**重发 Cookie**（刷新 `Max-Age`）。
- **节流**：只在"剩余不足阈值"时才写库 + 重发，避免每个请求都 `UPDATE`。
- 另一条路是"短会话（如 2h）+ refresh token"（双令牌），本轮不做。

### B.5 登出 / 踢设备

- **登出**：`revoked_at = now` + `response.delete_cookie("session")`。
- **全端登出 / 改密**：`UPDATE user_sessions SET revoked_at = now WHERE user_id = ?`（**改密必须做**）。
- **清理**：定期删 `expires_at < now` 的行（定时任务，或手动 SQL）。

### B.6 "记住我"

- 勾选 → `max_age = 7 天`（持久 Cookie）。
- 不勾 → **不设 `max_age`**（会话 Cookie，关浏览器即失效）。

### B.7 安全要点（对照契约 §3）

1. Cookie **只放原始 token**，库里只存 **sha256**（泄库也无法直接盗用会话）。
2. `HttpOnly`（防 XSS 读 Cookie）+ `SameSite=Lax`（挡大部分 CSRF）+ 生产 `Secure`。
3. **CSRF**：`SameSite=Lax` 之外，状态变更接口建议再校验自定义头（如 `X-Requested-With`）或双提交 token。
4. **会话固定**：登录后新发会话。
5. **时间口径统一 UTC** —— 若混用 `datetime.now()`（本地）与 `utcnow()`，跨时区会算错（ACTP 有过时间偏差的教训）。
6. 索引：`token_hash` 唯一、`user_id` 普通索引。

### B.8 前端联调（关键）

- 浏览器会**自动带 Cookie**，前端不用手动管 token —— 这是 Session Cookie 相对 JWT 最省事的地方。
- 但 fetch / axios 必须 **`credentials: 'include'` / `withCredentials: true`**。
- **开发期强烈建议用 Vite 代理**：把 `/api` 代理到 `http://127.0.0.1:8000`，前后端同源 → Cookie 无跨域烦恼。
  ```js
  // vite.config.js
  server: {
    proxy: { '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true } },
  }
  ```
- 若坚持跨域：后端 CORS 必须 `allow_credentials=True`，且 `allow_origins` 写**具体源**（**不能用 `*`**），前端带 `credentials`。

### B.9 雷点

1. **别把会话存进程内存**（多 worker 失效）—— 用 MySQL（已定）。
2. `set_cookie` 必须拿到 `Response` 对象：用 `response: Response` 参数或返回 `JSONResponse`，否则设不上。
3. `SameSite=None` 必须配 `Secure=True`，否则浏览器直接丢弃 Cookie。
4. 会话表要能清理，否则无限增长。
5. `Cookie(alias="session")` 的 `alias` 要与 `set_cookie(key=...)` 完全一致，写错就永远取不到。
