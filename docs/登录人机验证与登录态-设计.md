## A. 人机验证（验证码）

> 🔄 **2026-09-28 整体重写（自研无状态图形码版）**。上一版（2026-09-24）是**极验 GT4 滑块**，**已废弃**。
> 废弃原因：极验**注册账号要走审核**（国内站被吐槽「注册无响应 / 需要审核 / 客服没人」）——**换回自研，是为了不再被厂商流程卡住**。
> 写法上仍是「**后端出题、后端判卷**」，但**答案不再进 Redis，而是进签名（HMAC 自证）** → 见 A.2 / A.3。

### A.1 方案选择：为什么换回来，换回来得到什么、又付出什么

**直接原因**：极验**注册账号要走审核**。等审核不是本轮该花的时间。

**收益（四条，都是"减依赖"）**：

1. **零外部依赖** —— 厂商抖动不再影响登录 → **也就不存在 fail-open / fail-closed 这个纠结**（见 A.5）。
2. **`GET /auth/captcha` 接口重新成立** —— 极验版是「前端出题判卷、后端向厂商复核」，方向一反，后端不再生成图片，那个接口**整个不成立**（v2 已论证）。改回自研 = 「后端出题、后端判卷」，接口自然回来。
3. **不需要 `httpx`** —— 省掉一个运行依赖（极验版要把它从 dev 提到运行依赖）。
4. **不需要域名白名单** —— 没有厂商后台要配。

**代价（如实写）**：**强度低于行为验证**。静态图片对 OCR 只是**有限抵抗**——你们在 **ACTP 用 cnocr 破过若依的图形码**，这条经验有效、别自欺；且**生成与校验都要自己写**（见 A.4）。

| 方案 | 抗破解 | 后端依赖 | 结论 |
|---|---|---|---|
| **自研无状态图形码（Pillow + HMAC）** | 中低（抗 OCR 有限） | Pillow（`requirements.txt` 已有） | ✅ **本轮采用** |
| 极验 GT4 | 高 | `httpx` + 厂商账号**要审核** | ❌ 放弃（卡在注册审核） |
| 腾讯云验证码 | 高 | 官方 Python SDK **是同步的** | ❌ 在异步项目里会阻塞事件循环 |

> 📌 **一句话**：这次不是"从强到弱"的妥协，而是**用可接受的强度损失，换掉一整套外部流程与运行依赖**。
> 强度问题由 M6 限流兜底（见 A.2 附）。

### A.2 与若依（RuoYi）的对照：仿它，但比它少一套依赖

| | 若依 | 本项目 |
|---|---|---|
| 生成 | `GET /captchaImage` → uuid + Kaptcha 画图 | `GET /auth/captcha` → `captcha_token` + Pillow 画图 |
| **答案存哪** | 🔴 **Redis**：`captcha_codes:{uuid}`，TTL 2 分钟 | ✅ **不存**，答案在签名里，靠 **HMAC 自证** |
| 为什么它要存 | 集群下必须共享答案（有源码解析记载：早期用本地缓存，一上集群就报「验证码不存在或已过期」） | 无状态天然支持**多进程 / 多机** |
| 一次性 | 靠 Redis 删除 | 靠 **120 秒时间窗** |
| 默认题型 | `math`（算式，如 `2*3=?@6`；它的答案空间同样很小，这是**不跟它学**的一处） | **4 位字符码**（空间 32⁴ ≈ 105 万） |

> 📌 **对照的落点在第 2 行**：若依"存 Redis"是**被迫**的（集群要共享答案），不是设计偏好。
> 我们把答案挪进签名 → **既拿到了集群友好，又去掉了 Redis 这个依赖**。
> 代价是**做不了"用过即删"**，用**时间窗**替代 → 这条取舍写在 A.5，不藏着。

**附：分层防护 —— 本轮做哪层（口径未变）**

| 层 | 做什么 | 本轮 | 为什么 |
|---|---|---|---|
| 1 | **限流**（IP + email 计数） | ⬜ **归 M6** | `开发流程.md` §2 已把「限流」列为 M6 交付物 |
| 2 | **验证码** | ✅ **本轮** | 自研无状态图形码（本节） |
| 3 | **连续失败锁定** | ⬜ 后续 | 需 Redis 计数，与限流同批设计 |

**每次登录都要验证码，还是失败 N 次后才要？本轮定：每次都过。** 理由（不变）：
- 「失败 N 次后才要」需要前端先问后端"这次要不要验证码" → **多一个探测接口**，而它本身会泄露"该邮箱是否已被锁定"——**为一个体验优化开一个新的信息泄露面，不划算**。
- 前端还要维护"上次失败了没有"的状态，前后端状态同步是额外的 bug 源。
- 登录不是高频操作，填一次图形码的成本可接受。

> ⚠️ **因此本轮不需要 Redis**。「连续失败锁定」「限流」都要 Redis 计数 → 一并归 M6。
> **`fast` 环境本轮也不用装 `redis` 包**（`requirements.txt` 里已列出，但本轮不依赖）。

### A.3 流程与形状

**四段流程（全在本项目内，不跨厂商）**：
```
① 前端  进登录页 → GET /auth/captcha
② 后端  生成 4 位字符码 + 画图 → 返回 { captcha_token, image_base64 }   ← 无存储
③ 前端  显示图片；用户填答案；提交 POST /auth/login 时带 captcha_token + captcha_code
④ 后端  本地验签比对（不调任何外部服务）
```
**接口字段以 `docs/用户注册与登录-接口契约.md` §2.2 / §2.5 为准**（那里是唯一事实源，本节只讲形状与理由）。

**`captcha_token` 的构成（方案核心 —— 答案就在签名里自证）**：
```
token = f"{salt}.{ts}.{sig}"
salt  = secrets.token_hex(8)                                         # 每次随机
ts    = int(time.time())                                             # 签发时刻
sig   = hmac_sha256(CAPTCHA_KEY, f"{salt}.{ts}.{code}").hexdigest()   # code = 正确答案
```

**服务端校验（④ 的形状）**：
```
① 拆 token → salt / ts / sig
② 时限：now - ts <= 120s，否则 40002
③ 重算：expect = hmac_sha256(CAPTCHA_KEY, f"{salt}.{ts}.{用户输入}")
④ 常量时间比对：hmac.compare_digest(expect, sig)
```

> 🔴 **答案 `code` 不出后端** —— token 里只有签名，前端解开也拿不到答案。
> **全程不需要任何存储**：没有 Redis、没有内存字典、也不写 MySQL。
> 这也是为什么它**天然支持多进程 / 多机**——每个 worker 拿同一个 `CAPTCHA_KEY` 就能独立判卷。

### A.4 安全与实现要点

**四条硬约束（每条都要知道"不这么做会怎样"）**：

| # | 约束 | 不这么做会怎样 |
|---|---|---|
| 1 | token 必须带 `ts`，服务端限 **≤120 秒** | 无状态 token **无法作废**；不带时限的话，攻击者可以先囤一批图、慢慢 OCR 出答案，再回头拿 token 登录 —— **验证码形同不存在** |
| 2 | `salt` 每次随机 | 答案取值空间小（纯数字码只 10⁴ 种）；不加盐 → `sig` 与答案**一一对应** → **彩虹表秒破** |
| 3 | 必须用 `hmac.compare_digest`，**不能用 `==`** | `==` 是短路比较、逐字节提前返回 → **时序侧信道**，可被逐位猜出签名 |
| 4 | **统一转大写再比对**（`user_input.strip().upper()`） | 用户输小写 `ab3d` 会被判错 —— 而字符集本身只有大写，纯属为难人 |

**实现细节**：

- **题型：4 位字符码**（2026-09-28 实测后从「算式」改过来）。字符集 **`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`**（32 个：24 个字母去掉易混的 `I` / `O`，数字只用 `2-9` 去掉 `0` / `1`）。
  - **答案空间 = 32⁴ = 1,048,576**，盲猜通过率约百万分之一。
  - 🔴 **为什么不用算式**：算式结果恒落在 0–20，**答案空间只有 19 种**，盲猜通过率 **≈5.3%（1/19）** —— 攻击者不看图、随便填个数字就有 5% 过关。字符码的空间比它大 **5 个数量级**。（"算式要多理解一层"这个说法站不住：OCR 认出题面后一行 `eval` 就完事。）
- **字体**用 `ImageFont.load_default(size=36)`（Pillow ≥ 10.1 才支持传 `size`，本项目 `Pillow>=10.3` ✅）。
  - 🔴 **不要用 `ImageFont.truetype("C:/Windows/Fonts/...")`** —— 本地能跑，**Linux 部署时路径不存在会直接崩**。
- **干扰**：随机若干条直线 + 每个字符随机纵向偏移（**不做逐字旋转**，成本高收益低）。
- **`CAPTCHA_KEY`**：放 `.env`，用 `secrets.token_urlsafe(32)` 生成，**只在后端**、**不进日志**。
  - ⚠️ 本方案**没有 `CAPTCHA_ID`**（不存在"可公开给前端的 ID"这回事）—— 改极验时预留的那个键**不要加**。
- **失败文案统一** `400 / 40002`「人机验证失败，请重试」，**不要把"已过期"和"答案错"分开告诉用户**（这个区分**只对攻击者有用**）。前端在**任何登录失败后都刷新验证码**。
- **`GET /auth/captcha` 是公开接口**，本身可能被刷；**限流归 M6**（见 A.2 附）。

**顺序（安全边界，不能换）**：验证码校验**必须在查库之前**。
倒过来的话，攻击者不用过验证码就能拿 `/auth/login` 刷你的数据库。

### A.5 已知取舍：无状态 token 的 120 秒复用窗口

> ⚠️ **无状态 token 在 120 秒内可被复用**（没有服务端"用过即删"）。攻击者拿到一次 token 后，窗口内可反复提交。
> **目前接受**：bcrypt `cost=12` 单次约 185ms → 120 秒最多试 **~650 次**，对 6–18 位含字母数字的密码**没有实际收益**。
> **M6 限流落地后**这个窗口会进一步收窄。
> 若将来要求"绝对一次性"，再引入 Redis 存已用签名 —— **不做提前设计**。

> 📌 **顺带说明**：改自研方案后，「厂商不可用时 fail-open 还是 fail-closed」这个问题**自动消失**（没有外部厂商了）。
> 原极验时代的讨论保留在 `docs/用户注册与登录-接口契约.md` §7.3-B6 里作**沿革记录**。

## B. 登录态维持（Session Cookie）

### B.1 生命周期（四环节）

见对话中的流程图：

1. **登录成功 → 发会话**：生成随机 `token`（给浏览器），库里只存 `sha256(token)`（给数据库），`Set-Cookie`。
2. **后续请求 → 校验**：浏览器自动带 Cookie → 依赖查 `user_sessions` 有效则放行，否则 `401/40101`。
3. **临近过期 → 滑动续期**：延长 `expire_time` 并重发 Cookie（节流：剩余不足 3 天才续）。
4. **登出 / 踢设备 → 失效**：置 `revoke_time` + 清 Cookie；改密 / 全端登出 = 按 `user_id` 批量失效。

### B.2 登录成功：发会话

```python
import hashlib
import secrets
from datetime import datetime, timedelta, timezone

token = secrets.token_urlsafe(32)                        # 给浏览器
token_hash = hashlib.sha256(token.encode()).hexdigest()  # 给数据库
expire_time = datetime.now(timezone.utc) + timedelta(days=7)

session.add(UserSession(
    user_id=user.id,
    token_hash=token_hash,
    expire_time=expire_time,
))
await session.commit()

response.set_cookie(
    key="session_token",
    value=token,
    httponly=True,
    samesite="lax",
    secure=settings.cookie_secure,      # 生产 True
    max_age=7 * 24 * 3600,
    path="/",
)
```

> **会话固定防护**：登录成功后**新发一个会话**，绝不复用登录前的任何标识 —— 标准做法。

### B.3 每次请求：校验依赖

```python
from fastapi import Cookie, Depends


async def get_current_user(
    session: SessionDep,
    session_token: str | None = Cookie(default=None, alias="session_token"),
) -> User:
    if not session_token:
        raise BizError(ErrorCode.SESSION_INVALID, "未登录")

    token_hash = hashlib.sha256(session_token.encode()).hexdigest()
    row = await session.scalar(
        select(UserSession).where(
            UserSession.token_hash == token_hash,
            UserSession.revoke_time.is_(None),
            UserSession.expire_time > datetime.now(timezone.utc),
        )
    )
    if row is None:
        raise BizError(ErrorCode.SESSION_INVALID, "会话失效，请重新登录")

    user = await session.get(User, row.user_id)
    if user is None:
        raise BizError(ErrorCode.SESSION_INVALID, "账号不可用")
    return user
```

> ⚠️ **2026-09-24 口径校正（三处）**：
> ① 列名跟契约 §1.2 走：`expire_time` / `revoke_time`（原稿写 `expires_at` / `revoked_at`）。
> ② 异常用项目自己的 **`BizError(ErrorCode.…)`**（`app/core/errors.py`），**没有 `AuthError` 这个类**——原稿的 `AuthError` 是伪代码占位。
> ③ `datetime.now(timezone.utc)` 得到的是 **aware datetime**，而库里是**朴素 UTC**（`DATETIME`）→ 比较时**要去掉 tzinfo**（`datetime.now(timezone.utc).replace(tzinfo=None)`），否则 SQLAlchemy 会带时区去比，行为依赖驱动。**这一条务必自测**。

> ⚠️ **2026-09-20 修订**：原伪代码是 `if user is None or user.status != 1 or user.deleted_at is not None`。
> `status` 与 `deleted_at` 两字段**已从 `users` 表删除**（契约 §1.1.1）——照原样写会 `AttributeError`。
> 将来若真做「封号」或「注销」，把这两列加回（INSTANT，不重建表），再把这个条件补回来。

### B.4 持续 / 续期：滑动过期（sliding expiration）

- **纯固定 7 天**：简单，但第 7 天必然被踢，体验差。
- **滑动续期（推荐）**：校验通过后，若 `expire_time - now < 3 天`，则把 `expire_time` 顺延为 `now + 7 天`，并**重发 Cookie**（刷新 `Max-Age`）。
- **节流**：只在"剩余不足阈值"时才写库 + 重发，避免每个请求都 `UPDATE`。
- 另一条路是"短会话（如 2h）+ refresh token"（双令牌），本轮不做。

### B.5 登出 / 踢设备

- **登出**：`revoke_time = now` + `response.delete_cookie("session")`。
- **全端登出 / 改密**：`UPDATE user_sessions SET revoke_time = now WHERE user_id = ?`（**改密必须做**）。
- **清理**：定期删 `expire_time < now` 的行（定时任务，或手动 SQL）。

### B.6 "记住我"

- 勾选 → `max_age = 7 天`（持久 Cookie）。
- 不勾 → **不设 `max_age`**（会话 Cookie，关浏览器即失效）。

### B.7 安全要点（对照契约 §3）

1. Cookie **只放原始 token**，库里只存 **sha256**（泄库也无法直接盗用会话）。
2. `HttpOnly`（防 XSS 读 Cookie）+ `SameSite=Lax`（挡大部分 CSRF）+ 生产 `Secure`。
3. **CSRF**：`SameSite=Lax` 之外，状态变更接口建议再校验自定义头（如 `X-Requested-With`）或双提交 token。
4. **会话固定**：登录后新发会话。
5. **时间口径统一 UTC** —— 若混用 `datetime.now()`（本地）与 `utcnow()`，跨时区会算错（ACTP 有过时间偏差的教训）。
6. 索引：`token_hash` 唯一、`user_id` 普通索引。

### B.8 前端联调（关键）

- 浏览器会**自动带 Cookie**，前端不用手动管 token —— 这是 Session Cookie 相对 JWT 最省事的地方。
- 但 fetch / axios 必须 **`credentials: 'include'` / `withCredentials: true`**。
  ✅ **实测 2026-09-24：`frontend-web/src/utils/api.js` 已经带上了**（`credentials: 'include'`）——前端这块已就绪。
- **开发期用 Vite 代理**：把 `/auth` 代理到 `http://127.0.0.1:8000`，前后端同源 → Cookie 无跨域烦恼。
  ✅ **实测已配**（`frontend-web/vite.config.js`）：
  ```js
  server: {
    proxy: { '/auth': { target: 'http://127.0.0.1:8000', changeOrigin: true } },
  }
  ```
  > ⚠️ 注意代理的是 **`/auth`** 而不是 `/api`——因为后端路由前缀就是 `/auth/*`（契约 §2.0）。
  > **`/auth/me` 也在同一个前缀下，所以代理不用改。** 这正是当初把 `/me` 挂在 `auth_router` 的一个附带好处。
- 若坚持跨域：后端 CORS 必须 `allow_credentials=True`，且 `allow_origins` 写**具体源**（**不能用 `*`**），前端带 `credentials`。
  > ⚠️ 补充：一旦用了 Cookie 会话，**`allow_origins=["*"]` 与 `allow_credentials=True` 不能共存**（浏览器会直接拒绝），
  > 且 `SameSite=Lax` 在跨站请求里**不会发送** Cookie → 跨域部署要改成 `SameSite=None; Secure`（**必须 HTTPS**）。
  > **结论：开发期就走 Vite 代理同源，别碰跨域。**

### B.9 雷点

1. **别把会话存进程内存**（多 worker 失效）—— 用 MySQL（已定）。
2. `set_cookie` 必须拿到 `Response` 对象：用 `response: Response` 参数或返回 `JSONResponse`，否则设不上。
3. `SameSite=None` 必须配 `Secure=True`，否则浏览器直接丢弃 Cookie。
4. 会话表要能清理，否则无限增长。
5. `Cookie(alias="session_token")` 的 `alias` 要与 `set_cookie(key=...)` 完全一致，写错就永远取不到。

## D. 第 2 轮施工顺序（登录态 + 验证码 · 2026-09-24 定）

> 📌 **第 1 轮（注册 + 登录）已结**：端到端实测通过，收尾项已清（实测见契约 §7.3-C）。

### D.0 本轮范围边界

| | 内容 |
|---|---|
| ✅ 做 | 会话（`user_sessions` 表 → `Set-Cookie` → `get_current_user` → `/auth/me` → 登出 → 滑动续期）+ 验证码（**自研无状态图形码**）+ 前端登录态收口 |

### D.1 施工顺序（顺序即依赖方向，不能换）

```
① 依赖与配置    requirements.txt **不再需要 httpx**；.env 加 CAPTCHA_KEY（**不加 CAPTCHA_ID**）；
               config.py 加对应字段 → ⚠️ 先确认 .gitignore 挡住 .env
② 模型与迁移    app/models/user_session.py（按契约 §1.2）→ models/__init__.py 补 import
               → alembic revision --autogenerate → 人工逐行审 → upgrade head
③ 安全工具      core/security.py 加 token 生成/哈希（secrets.token_urlsafe(32) + sha256 hex）
               验证码独立成 core/captcha.py：**生成 + 校验两个函数，唯一出处**
④ 依赖注入      dependence.py 加 get_current_user（**公共依赖，放这里**，不放 router）
⑤ 接口          log_in.py：login 加验证码校验 + 建 session + Set-Cookie；
               新增 /auth/me、/auth/logout；**新增 GET /auth/captcha**
⑥ 前端          路由守卫 + 用 /auth/me 恢复登录态，替换 AuthView.vue 里的 localStorage 占位
⑦ 自测+真实验证  pytest（契约 §6 清单）+ curl 真起服务验 Cookie 往返
```

**每一步「为什么必须在这个位置」**：

| 步 | 为什么不能提前 / 推后 |
|---|---|
| ① | `.env` 与 `config.py` 是**所有后续步骤的输入**。且"密钥不能入库"这条**必须最先确认**——一旦 commit 出去就收不回来 |
| ② | **迁移先于代码**：模型不落地，`login` 里就没法 `session.add(UserSession(...))`。且迁移要**人工逐行审**——`--autogenerate` 会漏东西（`users` 那轮就撞过 `server_default` 假 diff） |
| ③ | `core/captcha.py` 是**纯函数**（生成 + 校验），**不依赖 session、不依赖路由** → 可以先写完**单独测通**（自己画一张图、自己验一次签）再拿到接口里用。**本轮没有外部依赖了，更该先把这块"证明能跑"** |
| ④ | `get_current_user` **必须住 `dependence.py`**：`/auth/me` 要它、`/auth/logout` 要它、将来别的 router 也要它。放 `router/log_in.py` 里会让别人 import router → 分组糊掉 |
| ⑤ | 到这一步前面全就绪，路由只做「接参 → 调 → 包信封」 |
| ⑥ | **契约 §7 #5 拍板：后端 `/auth/me` 跑通后再做前端**。倒过来的话，前端要拿一个不存在的接口反复试错 |
| ⑦ | `curl` 不能省：Cookie 往返（`Set-Cookie` → 浏览器带 `Cookie`）是**真实 HTTP 栈行为**，TestClient 测不到 |

### D.3 本轮验收标准

**第 1 轮已有**（保持）：注册 / 重复注册 / 大小写归一 / 非法邮箱弱密码 / 登录成功 / 错密码 / 防枚举 / 哈希非明文。

**本轮新增**：

- [ ] 登录响应带 `Set-Cookie: session_token=…; HttpOnly; SameSite=Lax; Path=/`
- [ ] 库里 `user_sessions.token_hash` 是 64 位 hex，**不等于** Cookie 里的原文（泄库≠可盗用）
- [ ] 带 Cookie 访问 `/auth/me` → `200`，`data` 含 `id / user_email / username / create_time`，**物理上不含** `password_hash`
- [ ] 不带 Cookie / 乱造 Cookie → `401 / 40101`
- [ ] 登出 → `200`；**登出后再访问 `/auth/me` → `401`**；**不带 Cookie 登出也返回 `200`**（幂等）
- [ ] **`GET /auth/captcha` 返回 `captcha_token` + `image_base64`，且库里无任何写入**（证明"无状态"）
- [ ] **过期 token（`ts` 超过 120 秒）→ `400 / 40002`**
- [ ] **改一个字节的 `sig` → `400 / 40002`**（证明签名真的在校验，不是摆设）
- [ ] **同一 token 配错答案 → `40002`；配对答案 → 放行**（证明是"验签 + 比对"两件事，不是只看签名）
- [ ] 验证码不过 + 密码也错 → 返回 **`40002` 而不是 `40102`**（证明顺序在查库之前）
- [ ] `create_time` 在响应里带 `Z`，前端 `new Date()` 解析后不差 8 小时（证明没被当本地时间）
