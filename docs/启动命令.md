## 2. 后端启动

### 日常开发（推荐）

```cmd
python -m uvicorn app.main:app --port 8000 --reload --no-access-log
```

| 参数 | 作用 |
|---|---|
| `python -m uvicorn` | 用 `(fast)` 环境里的 uvicorn（Windows conda 下最稳的调用方式） |
| `--reload` | 改 `.py` 自动重启（开发期专用） |
| `--no-access-log` | 关掉 uvicorn 原生的状态码行——它没有时间戳、没有 trace_id，会和 `app.access` 的访问日志重复 |

### 备选：`fastapi run --port 8000`

功能正常，**但控制台不会显示 `app.access` 访问日志**（fastapi CLI 的 rich 终端接管会吞掉它，2026-09-30 实测确认）。
不看日志时（挂着联调）用哪个都行；要看日志就用上面那条。

### 生产式启动（验收 / 压测）

```cmd
python -m uvicorn app.main:app --port 8000 --no-access-log
```

（不开 `--reload`，行为最接近真实部署。）

## 6. RAG 索引任务链路（三个进程，缺一不可）

索引链路要跑起来需要**三个独立进程**。少任何一个的表现各不相同，别混：

| 进程 | 启动命令 | 不启动的表现 |
|---|---|---|
| ① Web | 见 §2 | 页面打不开 |
| ② **索引 worker** | `arq app.worker.WorkerSettings` | **商品状态卡在 PENDING 永不变化**；不报错 |
| ③ **补偿 reaper** | `python -m app.worker_reaper` | 平时看不出；**Redis 投递失败 / worker 崩过的商品永远修不回来** |

### 为什么 worker 不启动是「静默」的

没有 worker 时商品照存、状态照填 PENDING，只是不建向量。
检索时因「没有该商品的向量」而召回不到它——**不报错，只是检索不到**。

### reaper 什么时候必须开

三种情况reaper 是唯一的后悔药：
- Redis 投递瞬间失败（状态留 PENDING 等它捞）
- worker 崩溃 / 被 kill（状态卡 RUNNING）
- embedding 持续失败（状态 FAILED；key 修好后重捞）

开发阶段可以不常驻，但要记得偶尔跑一次补存量：

```cmd
python -c "import asyncio; from app.services.index_service import reap_once; print(asyncio.run(reap_once()))"
```

### 排查索引状态

```sql
-- MySQL：三张表任选其一
SELECT index_status, COUNT(*) FROM cart_item      GROUP BY index_status;
SELECT index_status, COUNT(*) FROM owned_item     GROUP BY index_status;
SELECT index_status, COUNT(*) FROM purchase_record GROUP BY index_status;
```

| 状态 | 含义 | 该做什么 |
|---|---|---|
| `PENDING` | 等索引 | 正常。worker 没起就一直 PENDING |
| `RUNNING` | 处理中 | 停超10 分钟 = worker 崩了，等 reaper |
| `SYNCED` | 已入库 | 正常 |
| `FAILED` | 失败 | **查向量模型配置**（key 失效 / 欠费 / 维度不符），修好后跑一次 reaper |

### ⚠️ 队列隔离：测试**不会**污染生产队列（2026-10-17 起）

**旧问题**：`tests/test_index_service.py` 里有两处**故意**保留 `enqueue_sync` 的真实实现
（mock 掉反而测不到「投递失败自己吞掉」这条降级路径），于是它们往 `arq:queue` 里塞了真任务。
跑完测试再起 worker，worker 会消费到**测试造的假用户数据**并**真调向量模型 API（要花钱）**。
实测跑一次全量测试留下 **39 个 `arq:job:*`**。

**现在的解法不是「记得清队列」（靠人记性，必然忘），而是队列隔离**：

| | 键名 | 谁监听 |
|---|---|---|
| 生产 | `arq:queue` | `worker.py` |
| 测试 | `arq:queue:pytest` | **没人监听** |

`tests/conftest.py` 在 `import app.*` **之前**设 `ARQ_QUEUE_NAME=arq:queue:pytest`，
`redis_client.get_pool()` 把它传给 `arq.create_pool(default_queue_name=...)`。

所以**测试任务永远不会被 worker 执行**，不需要任何手工清理。
实测验证：跑完 175 个测试，`arq:queue` 仍是 0 个任务，26 个任务全进了 `arq:queue:pytest`。

>⚠️ job 定义本身仍会写进 `arq:job:*` 键（arq 的设计如此），但**没人消费就不会执行**，
> 且它们会自然过期。下面这个脚本用来清掉它们，保持 Redis 干净。

```cmd
:: 看一眼有什么，不删
python scripts/clear_arq_queue.py --all --dry-run

:: 清生产 + 测试队列 + 所有 arq:job:* 定义键
python scripts/clear_arq_queue.py --all
```

🔴 **`arq:queue` 在 arq 0.28 是 zset（有序集合），不是 list**。
本文档曾写「用 `redis-cli DEL arq:queue`」并给了一段 `pool.delete()` 的 Python 备选——
`DEL` 对 zset 恰好能删，但**只删队列不删 `arq:job:*` 定义**，
会留下一堆垃圾键（很难排查「为什么 worker 不干活」）。现在统一用上面的脚本。

### 什么时候需要手动清队列

| 场景 | 原因 |
|---|---|
| 改了 `index_stale_seconds` 想立刻重投 | 老的 RUNNING 还没到超时 |
| worker 崩过，怀疑有脏任务 | 孤儿 job 定义一直留着 |
| Redis 里 `arq:job:*` 堆积 | 无害但难排查，清一下 |

## 8. 常见问题

| 现象 | 原因 / 解法 |
|---|---|
| 前端登录不通 | 后端没起在 **8000** 端口，或 vite 代理指向被改（应指 `127.0.0.1:8000`） |
| 控制台看不到访问日志 | 检查是不是用 `fastapi run` 启动 → 换 §2 的 uvicorn 命令 |
| 端口被占 | `netstat -ano | findstr :8000` 找 PID → `taskkill -F -FI "PID eq <pid>"` |
| `alembic heads` 出两行 | 迁移分叉了，处理见 AGENTS.md §5 |
