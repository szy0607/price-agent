# A4 对比 / A5 推荐 —— 设计方案

> 建立于 2026-10-18。起因：大宋提出「对比做成一个 Agent 但有一套评分标准，
> 通过分数对比；推荐不局限于用户的商品库」。
>
> **本文是这三块功能的设计依据**：A4 对比、A5 推荐、对话侧商品卡片。
> 读之前先看 §0 —— 那里记着几个「实测才知道」的前提，不看会踩坑。

## 0. 三条实测前提（2026-10-18 查证，都不是拍脑袋）

### 0.1 🔴 现有 `StreamEvent` 只有两种事件，没有「Agent 开始了」

```
StreamEvent.kind ∈ {"text", "tool_call"}
```

流式输出设计文档 §5.4 早就预留了 `agent` 事件的位置，但**至今没实现**。
A4/A5 要让用户看到「正在对比…」就需要第三种事件。这是三个功能**共同的前置改动**。

### 0.2 🔴 `web_search` 的返回结构（web_search_service.py）

```python
web_search(query, count=5) -> list[dict]
# 每项：{name, url, snippet, datePublished, summary}
```

**🔴 它返回的是「网页」不是「商品」。** `summary` 字段是博查对网页的摘要，
**不能直接当商品参数用** —— 要提参数还得走 `spec_complete_service.complete_specs`
（它内部就是 `web_search` + 主模型提取）。

⚠️ 这意味着**一次推荐的调用链是**：
```
web_search(找候选商品)          ← 1 次博查
  → 主模型提取规格（每个候选）    ← N 次主模型调用
```
**成本 = 1×0.036 + N×主模型费**。N 怎么定见 §4.3。

### 0.3 🔴 库里商品数与品类分布（决定了「对比」能不能做）

```
购物车 25 件 · 物品库 21 件 · 消费记录 21 件
品类：数码 10 · 家电 7 · 运动户外 6 · 家居 5 · 美妆 4 · 服饰 2 · 其他 2
PG 向量：1 条
```

**🔴 A4 的前提是「同一品类有 2+ 件商品」**。目前跨表凑不齐几组完整的
（且 transfer 关系会让同一件商品在两个表里）。**A4 做出来会经常「无可对比」**。

这不是「不做 A4」的理由（联网搜索能补候选），但**决定了 A4 的一半流程要走 A5 的联网路径**。

## 1. 大宋 18:20 的三个决定

| # | 决定 | 说明 |
|---|---|---|
| 1 | **对比走「分维度」而非单一总分** | 我提议、大宋接受。理由见 §2.1 |
| 2 | **推荐走博查联网** | 「不局限于用户的商品库」的实现路径 |
| 3 | **做完 A4/A5 再做卡片** | 顺序定下来了 |

**关于第 1 条我要把反对意见留档**：大宋最初的想法是「一套评分标准，通过分数对比」。
我反对的是**硬编码的评分表**（品类不同维度不同、加一个品类改一次代码、
权重没有实测依据、分数会「假装客观」）。
大宋接受的替代方案是：**评分标准由模型按品类现场生成，但要分维度可解释**。
**如果将来大宋要改回总分，本文的 §2.1 是当时的判断依据。**

## 2. A4 对比

### 2.1 为什么分维度而不是总分

**总分掩盖真实差异。** 假设两件商品：

```
真实情况：索尼降噪 9 分 / 佩戴 6 分
          AirPods 降噪 6 分 / 佩戴 9 分
总分算法：可能算出 7.5 vs 7.5 ——「打平」
```

用户看到「打平」就不知道该买哪个了。而**分维度对比直接说清「你更在意哪个」**。

**不这么写会怎样**：给总分 → 用户拿总分做决策 → 但总分掩盖了「一个降噪强、一个佩戴好」
这种需要他自己权衡的真实差异 → **决策信息变少了**。

**⚠️ 如果将来改成总分，必须同时约定**：分数旁边附上「按哪些维度、各占多少权重」，
否则就是伪客观（项目铁律里「双价透明」的同款逻辑）。

### 2.2 A4 的输入从哪来

两条路，**取决于用户勾选了什么**：

| 用户操作 | A4 用什么 | 要不要联网 |
|---|---|---|
| 勾选了 2+ 件自己的商品 | 直接用 `fetch_items_for_refs` 的结果 | ❌ 不需要 |
| 只说了「索尼和 AirPods 哪个好」 | 联网搜这两件 → `complete_specs` 提参数 | ✅ 2 次搜索 |

**⚠️ 第二条的成本**：2 个候选 = 2 次博查（~0.072 元）+ 2 次主模型调用。
`spec_complete_service` 现在是**单商品**函数，A4 需要包一层循环。

### 2.3 A4 的输出形态

```
【对比：索尼 WH-1000XM5  vs  Apple AirPods Pro 2】
┌──────────────┬──────────┬──────────┐
│ 维度          │ 索尼      │ AirPods  │
├──────────────┼──────────┼──────────┤
│ 主动降噪     │ 强        │ 中        │  ← 索尼占优
│ 佩戴舒适     │ 中│ 强        │  ← AirPods 占优
│ 续航         │ 30h       │ 6h(带盒)  │  ← 索尼占优
│ 重量          │ 250g      │ 61g       │  ← AirPods 占优
└──────────────┴──────────┴──────────┘
按你的需求（我看你常买降噪好的），索尼更合适。
⚠️ 参数来源：网络（博查），仅供比较参考
```

**🔴 必须带「参数来源：网络」** —— 与 `spec_complete_service` 的 `(AI)` 后缀同一套合规口径。

### 2.4 A4 怎么接进图

**它是一个新的 LangGraph 节点，不是新工具。** 理由（`Agent编号约定.md` 的三件套标准）：
A4 有自己的判断逻辑（维度选择）+ 自己的 prompt + 自己的输入。

```
START → decide ─┬─ 要检索 → search ─┐
                ├─ 要对比 → compare ─┤   ← 新增
                └─ 直接答 → END      ↓
                          decide（把对比结果带进上下文）
```

⚠️ **`MAX_ROUNDS` 要从 2 提到 3**（检索 2 次 + 对比 1 次），
`RECURSION_LIMIT` 跟着重算 —— 这个数是 `(MAX_ROUNDS+1)*2+2`，改完**必须实测**别凭直觉。

## 3. A5 推荐

### 3.1 「不局限于用户商品库」改变了什么

原定义是「根据画像推荐买什么」，隐含候选**从用户库里来**。
大宋的要求是**能推用户没有的东西**，所以候选来源必须是**联网**。

```
① 画像 + 行为证据     → profile_service（已有）
② 从画像推出搜索词     → 主模型（例：「喜欢降噪、预算 2000 以内」）
③ 联网搜候选商品       → web_search（1-3 次）
④ 提参数              → complete_specs（每候选 1 次主模型）
⑤ 按画像匹配度排序     → 主模型
⑥ 输出推荐 + 理由 + 来源
```

**🔴 这是 3 段共 4-6 次模型调用 + 1-3 次博查。单次推荐成本约 0.1-0.2 元。**

### 3.2 🔴 合规红线（与 AI 联网补全同一套）

| 红线 | 推荐场景的具体含义 |
|---|---|
| **零交易动作** | 推荐 ≠ 下单。**必须有「加入购物车」让用户自己点**，系统绝不自动入库 |
| **不给 CPS 链接** | `web_search` 返回的 `url` 是网页地址，**可能带返佣**。**绝不能原样给用户** |
| **来源标记** | 参数必须标「来源：网络」，与 `spec_complete_service` 的 `(AI)` 后缀一致 |
| **不编造** | 联网没查到的参数**不能出现**。模型不知道就说「资料未提及」 |
| **隐私** | **绝不能把用户的画像/物品库内容发给博查** —— 搜索词只能是「降噪耳机 2000元」这种商品描述 |

**🔴 最后一条是最容易犯的错**：如果直接把「用户有 3 件索尼耳机」当搜索词发给博查，
**用户的购物数据就出境了**。搜索词必须是**从画像抽象出来的商品特征**，不是用户数据本身。

### 3.3 A5 的输出形态

```
按你的偏好（常买数码、看重续航、预算 2000 内），推荐：

【1. 索尼 WH-1000XM5  ¥2299】
   匹配理由：你之前买过索尼降噪耳机（物品库），同品牌续航口碑好
   关键参数：续航 30h · 重量 250g · 主动降噪
   ⚠️ 来源：网络，仅供参考 · 价格随渠道变动

【2. Apple AirPods Pro 2  ¥1899】
   匹配理由：轻（61g）适合通勤
   ...
```

**每个推荐都要有「匹配理由」并指向用户的真实数据**（哪个物品、哪次消费），
不能是泛泛的「性价比高」。

### 3.4 成本控制

| 控制点 | 建议 | 理由 |
|---|---|---|
| 单次推荐搜索次数 | **≤ 3** | 3×0.036 = 0.108 元 |
| 候选商品数 | **≤ 4** | 超过用户也不会看 |
| 主模型调用 | ≤ 5 | 每次约 1000-2000 token |
| **单用户日限次** | **待定** | 防止脚本刷爆 |

**⚠️ 限次这条我没给数字** —— 要看大宋愿意承担多少成本。**必须有个上限**，
否则一次恶意构造的提问就能烧掉几百元。

## 4. 三个功能共用的前置改动

### 4.1 🔴 `StreamEvent` 加第三种事件

```
kind: Literal["text", "tool_call", "agent"]
```

`agent` 事件承载「正在对比…」「正在推荐…」，前端渲染成一行转圈提示
（和现在 tool_calls 的可展开行同一个位置）。

**这是三个功能的共同前置**，必须先做。

### 4.2 卡片落地时的复用

对话侧商品卡片（`Agent编号约定.md` §5、§6）需要的三件事，**A5 做完就有了**：

```
① 联网搜候选 + 提参数   ← A5 的 ③④
② 草稿只在当前响应里   ← 新增一个 SSE 事件（card）
③ 用户点确认 → POST /cart/items   ← 已有接口
```

**所以顺序是 A4 → A5 → 卡片，卡片的联网部分不用重写。**
