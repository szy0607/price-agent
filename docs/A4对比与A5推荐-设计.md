# A4 对比 / A5 推荐 —— 设计方案

> 建立于 2026-10-18。起因：大宋提出「对比做成一个 Agent 但有一套评分标准，
> 通过分数对比；推荐不局限于用户的商品库」。
>
> **本文是这三块功能的设计依据**：A4 对比、A5 推荐、对话侧商品卡片。
> 读之前先看 §0 —— 那里记着几个「实测才知道」的前提，不看会踩坑。

## 0. 三条实测前提（2026-10-18 查证，都不是拍脑袋）

### 0.1 🔴 现有 `StreamEvent` 只有两种事件，没有「Agent 开始了」

```
StreamEvent.kind ∈ {"text", "tool_call"}
```

流式输出设计文档 §5.4 早就预留了 `agent` 事件的位置，但**至今没实现**。
A4/A5 要让用户看到「正在对比…」就需要第三种事件。这是三个功能**共同的前置改动**。

### 0.2 🔴 `web_search` 的返回结构（web_search_service.py）

```python
web_search(query, count=5) -> list[dict]
# 每项：{name, url, snippet, datePublished, summary}
```

**🔴 它返回的是「网页」不是「商品」。** `summary` 字段是博查对网页的摘要，
**不能直接当商品参数用** —— 要提参数还得走 `spec_complete_service.complete_specs`
（它内部就是 `web_search` + 主模型提取）。

⚠️ 这意味着**一次推荐的调用链是**：
```
web_search(找候选商品)          ← 1 次博查
  → 主模型提取规格（每个候选）    ← N 次主模型调用
```
**成本 = 1×0.036 + N×主模型费**。N 怎么定见 §4.3。

### 0.3 🔴 库里商品数与品类分布（决定了「对比」能不能做）

```
购物车 25 件 · 物品库 21 件 · 消费记录 21 件
品类：数码 10 · 家电 7 · 运动户外 6 · 家居 5 · 美妆 4 · 服饰 2 · 其他 2
PG 向量：1 条
```

**🔴 A4 的前提是「同一品类有 2+ 件商品」**。目前跨表凑不齐几组完整的
（且 transfer 关系会让同一件商品在两个表里）。**A4 做出来会经常「无可对比」**。

这不是「不做 A4」的理由（联网搜索能补候选），但**决定了 A4 的一半流程要走 A5 的联网路径**。

## 2. A4 对比

### 2.1 为什么分维度而不是总分

**总分掩盖真实差异。** 假设两件商品：

```
真实情况：索尼降噪 9 分 / 佩戴 6 分
          AirPods 降噪 6 分 / 佩戴 9 分
总分算法：可能算出 7.5 vs 7.5 ——「打平」
```

用户看到「打平」就不知道该买哪个了。而**分维度对比直接说清「你更在意哪个」**。

**不这么写会怎样**：给总分 → 用户拿总分做决策 → 但总分掩盖了「一个降噪强、一个佩戴好」
这种需要他自己权衡的真实差异 → **决策信息变少了**。

**⚠️ 如果将来改成总分，必须同时约定**：分数旁边附上「按哪些维度、各占多少权重」，
否则就是伪客观（项目铁律里「双价透明」的同款逻辑）。

### 2.2 🔴 维度由**用户具体问题**决定（大宋 22:40 拍板）

**同样两件降噪耳机，四种问法要对四套维度**：

| 用户问的 | 该用的维度 |
|---|---|
| 「索尼和 AirPods 哪个好」 | 降噪深度 / 续航 / 佩戴 |
| 「哪个戴久了耳朵不难受」 | **重量 / 耳压 / 贴合度** |
| 「出差带哪个」 | **续航 / 重量 / 便携** |
| 「预算 2000 以内」 | **价格 / 核心参数 / 性价比** |

**「按品类」不够**：降噪耳机都拿同一套（降噪/续航/佩戴），
但用户问「戴久了耳朵不难受」时他关心重量和耳压——**降噪再强也不答他的问题**。

#### 🔴 「用户问题」从哪来：走 `tool_calls` 的 arguments

**先看现有代码已经证明的路径**（`a1_graph.py` 的 `search` 节点）：

```python
for call in calls:                                  # state["tool_calls"]
    query = str(call.parsed_arguments().get("query") or "").strip()
```

**节点间传数据的现成通道就是 `tool_calls`** —— 模型决定调工具时，
它已经把理解的用户意图写进 `arguments` 了。所以 A4 这样做：

```python
# compare 节点
for call in calls:
    args = call.parsed_arguments()
    question = args["question"]     # "戴久了哪个更舒服" ——模型提炼过的意图
    items = args["items"][:3]       # 最多三件（大宋 22:40 拍板）
```

**三条路对比**：

| | 做法 | 评价 |
|---|---|---|
| A | 翻 `messages` 找最后一条 `role=="user"` | 🔴 末尾是 assistant 的 tool_calls 和 tool 结果，要往前跳；多轮后未必是本轮的 |
| B | 新增 `user_question` 状态字段 | 🔴 **多余** —— 参数里已经有了，且要多维护一个字段 |
| **C** | **读 `tool_calls[].parsed_arguments()["question"]`** | ✅ **零新增状态**，且拿到的是**模型提炼过的意图** |

**⚠️ C 比 A/B 更准**：翻 messages 拿到的是用户原话（长、含【用户引用商品】块）；
arguments 里是模型**浓缩过的**对比意图（短、聚焦）。

**⚠️ C 的前提：模型必须老实填 `question`。** 三道保险：

```
① 工具定义里 question 放进 "required"      ← 最硬的一道
② description 里写清「用户问的是什么」      ← 告诉模型这是什么
③ compare 节点读到空 question 时降级        ← 不报错，退回品类通用维度
```

**③ 的降级路径**：question 为空 → 用「商品品类」当维度依据 → 行为退化成
「按品类对比」，也就是我最早提的方案。**降级而不是报错**——维度生成失败不该
让整个对比失败。

### 2.3 A4 的输出形态

```
用户问：「戴久了耳朵不难受，哪个好？」
        ↓ 维度按这个问题定
【对比：索尼 WH-1000XM5  vs  Apple AirPods Pro 2】
┌──────────────┬──────────┬──────────┐
│ 维度          │ 索尼      │ AirPods  │
├──────────────┼──────────┼──────────┤
│ 单耳重量     │ 250g      │ 61g       │  ← AirPods 占优
│ 佩戴压力     │ 中│ 轻        │  ← AirPods 占优
│ 贴合度       │ 一般      │ 贴合较好  │  ← AirPods 占优
└──────────────┴──────────┴──────────┘
你问的是久戴舒适度，这三项 AirPods 都占优。
⚠️ 参数来源：网络（博查），仅供比较参考
```

**🔴 注意维度表里没有「降噪」**——用户没问降噪，对比表里就不该出现。
这是「维度跟问题走」的直接体现：**比品类通用表更聚焦，也更短**。

**🔴 必须带「参数来源：网络」** —— 与 `spec_complete_service` 的 `(AI)` 后缀同一套合规口径。

**⚠️ 维度上限**：模型最多给 **5 个维度**。理由：
- 7 个以上前端表格要横向滚动，手机上没法看
- 维度多说明模型在「凑数」而不是在回答问题

### 2.4 🔴 最多三件商品（大宋 22:40 拍板）

**三条约束，缺一不可**：

| 约束 | 做法 | 不这么写会怎样 |
|---|---|---|
| **工具层拦截** | `compare_items` 的 `items` 参数**最多 3 个**，超了报错 40001 | 超出的静默忽略 → 用户以为比了 5 件，其实只比了 3 件 |
| **提示要说清** | 报错文案告诉用户「最多对比 3 件，请挑最重要的」 | 只说「参数错误」→ 不知道怎么办 |
| **联网成本封顶** | 3 件 = **3 次博查上限**（~0.108 元） | 不封顶的话一个「帮我比 10 件」就烧掉 0.36 元 |

**⚠️ 与现有 `MAX_REFS` 的关系**：前端「引用商品」已有上限（`MAX_REFS`，
见 ChatView.vue）。A4 的三件上限是**独立的第二道闸**——
用户可以勾 5 件引用，但**要求对比时最多只能比 3 件**。

**⚠️ 三件够不够**：实际场景里对比超过 3 件（4-5 件）的决策质量会**急剧下降**——
用户记不住 5 个商品的差异，最后还是回到「随便挑一个」。所以三件不只是成本限制，
**也是体验上的正确取舍**。

### 2.5 A4 的输入从哪来

两条路，**取决于用户勾选了什么**：

| 用户操作 | A4 用什么 | 要不要联网 |
|---|---|---|
| 勾选了 2-3 件自己的商品 | 直接用 `fetch_items_for_refs` 的结果 | ❌ 不需要 |
| 只说了「索尼和 AirPods 哪个好」 | 联网搜这两件 → `complete_specs` 提参数 | ✅ 最多 3 次搜索 |

**⚠️ 第二条的成本**：3 个候选 = 3 次博查（~0.108 元）+ 3 次主模型调用。
`spec_complete_service` 现在是**单商品**函数，A4 需要包一层循环。

**⚠️ §0.3 那个数据现实直接影响这里**：库里 67 件商品但跨表凑不齐「同品类 2+ 件」，
所以**实际使用中「联网取参」这条路径会占大多数**，不是少数情况。

### 2.6 A4 怎么接进图

**它是一个新的 LangGraph 节点，不是新工具。** 理由（`Agent编号约定.md` 的三件套标准）：
A4 有自己的判断逻辑（维度选择）+ 自己的 prompt + 自己的输入。

```
START → decide ─┬─ 要检索 → search ────┐
                ├─ 要对比 → compare ────┤   ← 新增
                └─ 直接答 → END        ↓
                          decide（把对比结果带进上下文）
```

⚠️ **`MAX_ROUNDS` 要从 2 提到 3**（检索 2 次 + 对比 1 次），
`RECURSION_LIMIT` 跟着重算 —— 这个数是 `(MAX_ROUNDS+1)*2+2`，改完**必须实测**别凭直觉
（2026-10-17 实测：按轮数×2 算出 5 会撞，真值是 6）。

⚠️ **不新增状态字段**（见 §2.2 的方案 C）：`question` 从 `tool_calls` 的 arguments 读，
沿用 `search` 节点现成的 `call.parsed_arguments()` 写法。

## 3. A5 推荐

### 3.1 「不局限于用户商品库」改变了什么

原定义是「根据画像推荐买什么」，隐含候选**从用户库里来**。
大宋的要求是**能推用户没有的东西**，所以候选来源必须是**联网**。

```
① 画像 + 行为证据     → profile_service（已有）
② 从画像推出搜索词     → 主模型（例：「喜欢降噪、预算 2000 以内」）
③ 联网搜候选商品       → web_search（1-3 次）
④ 提参数              → complete_specs（每候选 1 次主模型）
⑤ 按画像匹配度排序     → 主模型
⑥ 输出推荐 + 理由 + 来源
```

**🔴 这是 3 段共 4-6 次模型调用 + 1-3 次博查。单次推荐成本约 0.1-0.2 元。**

### 3.2 🔴 合规红线（与 AI 联网补全同一套）

| 红线 | 推荐场景的具体含义 |
|---|---|
| **零交易动作** | 推荐 ≠ 下单。**必须有「加入购物车」让用户自己点**，系统绝不自动入库 |
| **不给 CPS 链接** | `web_search` 返回的 `url` 是网页地址，**可能带返佣**。**绝不能原样给用户** |
| **来源标记** | 参数必须标「来源：网络」，与 `spec_complete_service` 的 `(AI)` 后缀一致 |
| **不编造** | 联网没查到的参数**不能出现**。模型不知道就说「资料未提及」 |
| **隐私** | **绝不能把用户的画像/物品库内容发给博查** —— 搜索词只能是「降噪耳机 2000元」这种商品描述 |

**🔴 最后一条是最容易犯的错**：如果直接把「用户有 3 件索尼耳机」当搜索词发给博查，
**用户的购物数据就出境了**。搜索词必须是**从画像抽象出来的商品特征**，不是用户数据本身。

### 3.3 A5 的输出形态

```
按你的偏好（常买数码、看重续航、预算 2000 内），推荐：

【1. 索尼 WH-1000XM5  ¥2299】
   匹配理由：你之前买过索尼降噪耳机（物品库），同品牌续航口碑好
   关键参数：续航 30h · 重量 250g · 主动降噪
   ⚠️ 来源：网络，仅供参考 · 价格随渠道变动

【2. Apple AirPods Pro 2  ¥1899】
   匹配理由：轻（61g）适合通勤
   ...
```

**每个推荐都要有「匹配理由」并指向用户的真实数据**（哪个物品、哪次消费），
不能是泛泛的「性价比高」。

### 3.4 成本控制

| 控制点 | 决定 | 理由 |
|---|---|---|
| 单次推荐搜索次数 | **≤ 3** | 3×0.036 = 0.108 元 |
| 候选商品数 | **≤ 4** | 超过用户也不会看 |
| 主模型调用 | ≤ 5 | 每次约 1000-2000 token |
| **单用户日限次** | **⏸ 暂不做**（大宋 22:55 拍板） | 见下面的风险账 |

#### ⏸ 不做日限次的风险账（2026-10-18 实测）

**单次推荐成本上限 ≈ 0.2 元**（3 次博查 + 若干主模型调用）。

**理论最坏情况**（一个人恶意刷满限流）：

```
6 次/分钟 × 0.2 元 = 1.2 元/分钟 = 72 元/小时 = 1728 元/天
```

**但有两道现实约束把这个数压下来**：

|约束 | 说明 |
|---|---|
| ① 耗时 | 一次推荐要 4-6 次模型调用 + 3 次博查，**单次十几秒** → 60 秒窗口内发不满 6 次 |
| ② 限流是**进程内**的 | `rate_limit.py` 注释明说「多 worker 各自为政、每人一份账」→ 单 worker 有效，多 worker 稀释 N 倍 |

**现有限流实测参数**：`chat:{user_id}` **6 次 / 60 秒**（`app/router/chat.py:14-15`），
外加 `MAX_ROUNDS` 限制单轮工具调用次数。

**结论：demo /内部测试阶段够用。**

#### 🔴 必须在「上多worker」之前重做限次

**触发条件**（满足任一条就要做）：

| # | 触发条件 | 为什么 |
|---|---|---|
| 1 | **Web 服务上多 worker**（`uvicorn --workers N`） | 进程内限流被稀释 N 倍，等于没有 |
| 2 | **开放注册 / 上公网** | 现在限流只在「登录后」生效，但 demo 阶段账号是自己造的 |
| 3 | 观察到**单用户单日博查调用量异常** | 最直接的信号 |

**做的时候**：搬Redis（`rate_limit.py` 的 docstring 已经预留了这个方向——
「搬 Redis 是『上多 worker』那个触发点才该做的事，现在不提前铺路」）。
或者更精准的做法：**只给「花钱的工具」单独计数**（`web_search` 调用次数），
而不是给所有 chat 请求计数——**检索（RAG）不花钱，不该被联网的限流卡住**。

## 4. 三个功能共用的前置改动

### 4.1 🔴 `StreamEvent` 加第三种事件

```
kind: Literal["text", "tool_call", "agent"]
```

`agent` 事件承载「正在对比…」「正在推荐…」，前端渲染成一行转圈提示
（和现在 tool_calls 的可展开行同一个位置）。

**这是三个功能的共同前置**，必须先做。

### 4.2 卡片落地时的复用

对话侧商品卡片（`Agent编号约定.md` §5、§6）需要的三件事，**A5 做完就有了**：

```
① 联网搜候选 + 提参数   ← A5 的 ③④
② 草稿只在当前响应里   ← 新增一个 SSE 事件（card）
③ 用户点确认 → POST /cart/items   ← 已有接口
```

**所以顺序是 A4 → A5 → 卡片，卡片的联网部分不用重写。**
