## 1. 结论摘要

当前文档不是单点错误，而是三种内容混在了一起：

1. 已拍板的当前实现（MySQL、Session Cookie）；**已改为自研无状态图形码（2026-09-28 拍板），尚未实现**（代码中无 `app/core/captcha.py`，`app/schemas/user_sche.py:8-10` 的 `UserLogin` 只有 `user_email`/`password`）；
2. M3/M6 才会启用的未来组件（PostgreSQL/pgvector、Redis）；
3. 仍未验证的建议（缓存哪些数据、是否保存用户历史画像、是否需要跨库事务）。

这会造成两个直接风险：

- 开发者按 README/requirements.txt 误以为 Redis 现在就是必需基础设施；
- 开发者把 MySQL 与 PostgreSQL 当成一个逻辑数据库使用，后续写出跨库事务、跨库外键或没有补偿机制的双写。

建议把契约改成“当前启用组件 + 启用门槛 + 数据归属 + 禁止事项”四部分，而不是只列技术名词。

## 2. 必须先修正的文档问题

### 2.1 Redis 的启用时机（本轮已对齐）

原先多份文档对 Redis 启用时机的表述不一致，**本轮已随 README / requirements / 开发流程 / 设计方案 中对“Redis 启用时机与用途”的同步修正而对齐**。当前各处口径：

- `README.md` 技术栈：Redis（**M3/M6 起的缓存与临时状态**）；
- `requirements.txt`：Redis 归在“可选缓存 / 临时状态（**M3/M6 才启用**）”下，并注明“M0-M2 本地开发不要求 Redis 服务”；
- `开发流程.md`：Redis 仅用于 M3/M6 起的缓存与临时状态（M3 验收含“缓存 TTL 生效且 Redis 故障可回源”）；
- `docs/登录人机验证与登录态-设计.md`：明确“本轮不需要 Redis”；同一文件明确 Session 落 MySQL，而不是 Redis；限流归 M6；
- `智能电商采购Agent-设计方案.md`：Redis（M3/M6 起）。

**结论：启用时机已对齐**——M0-M2 不要求 Redis、M3 起做缓存、M6 起做限流/失败计数。启用**用途**的一致性分级仍待补（见 §2.2）。

**建议默认方案：**

- M0-M2：不要求 Redis，不在登录态中使用 Redis，不把 `redis` 作为当前必需依赖；
- M3：只有在真实联盟 API 接入后，定义并验证“价格/券响应缓存”才启用 Redis；
- M6：用 Redis 做 IP/email 限流、连续失败计数、分布式锁等短 TTL 状态；
- Session：继续落 MySQL。Redis 可以做读缓存，但不能成为会话事实源；
- Redis 不可用时：缓存场景应降级为直查 API/数据库，安全控制场景应 fail-closed 或明确限额，不能所有场景统一处理。

### 2.2 Redis 的用途没有按一致性等级分类

文档只写“券信息缓存、会话状态”，但两者一致性完全不同：

| 数据 | 是否事实源 | 可接受丢失 | 建议 |
|---|---|---:|---|
| 登录 Session | MySQL 是事实源 | Redis 丢失不能导致全员登出 | Redis 仅可选读缓存，不存唯一状态 |
| 联盟价格/券响应 | 联盟 API 是事实源 | 可丢失；过期必须不冒充实时价 | Redis，按平台/商品/请求参数分键，短 TTL |
| 限流计数 | Redis 是临时计数器 | 可按策略放宽或收紧 | Redis 原子 `INCR` + TTL |
| 验证码答案 | 当前方案不需要自存 | 不适用 | 自研图形码的答案同样不自存：靠 HMAC 签名自证（结构 `salt.ts.sig`），一次性靠 120 秒时间窗；不用 Redis |
| 任务队列/事件 | Redis 不是默认队列 | 需明确投递语义 | 未决定前不要引入 |

必须禁止把“缓存命中”直接当成“当前价格”，响应中要带 `source_time`、`expires_at` 或等价的新鲜度信息。

### 2.3 MySQL + PostgreSQL 的边界不完整

当前结论“业务 MySQL、知识/向量 PG”方向可以成立，但契约缺少以下硬规则：

- 一个业务实体只能有一个事实源；
- MySQL 与 PG 之间不建立外键；
- 不做跨库事务，不假设一次 `commit` 能同时提交两个库；
- PG 只保存知识文档、切片、embedding、检索元数据；
- 用户、订单、会话、审计主记录仍在 MySQL；
- PG 中若出现 `user_id`，只能作为不可约束的关联/过滤字段，且必须说明用途、保留期限和删除策略；
- 两个库各自独立迁移、备份、健康检查和连接池；
- 任何跨库同步必须是可重试、幂等、有失败记录的异步流程。

特别注意：设计方案把“用户历史画像（脱敏）”列入 RAG 知识源，但没有定义脱敏、授权、删除传播和是否允许进入 embedding。默认不应把用户私密对话直接写入共享知识库。

**建议默认方案：**M3 的 PG 先只承载平台规则、券知识、规格库等公共知识；用户画像留在 MySQL，按请求实时组装上下文。只有验证确有个性化检索收益后，另立决策增加“用户私有知识空间”，并定义租户隔离与删除协议。

### 2.4 PostgreSQL/pgvector 的启用门槛缺失

目前 M3 一开始就要求安装 PG、扩展、独立 Alembic 和 HNSW 验证，但尚未有：

- 供应商不可用时的重建策略；
- embedding 版本变更时如何全量重建；
- 公共知识规模、检索延迟和命中率基线；
- Windows 本地安装 pgvector 的团队可复制方案；
- PG 备份/恢复和扩展升级方案。

**建议默认方案：**PG/pgvector 在 M3-0 作为“RAG 开始前置条件”启用，但在 M1/M2 不安装、不引入代码依赖。M3-1 先完成可恢复的最小公共知识库，再决定 HNSW 参数；知识量和查询量不足时不要提前做复杂的跨库抽象。

## 3. 需要你商定的决策

以下事项会改变后续代码边界，建议逐项确认：

### D1：Redis 是否按上述分阶段启用？（已确认：是）

当前结论：**是**。M0-M2 不要求 Redis；M3 为联盟 API 缓存和对话最近消息热缓存引入；M6 再补限流/失败计数。  
反对该方案的理由通常只有一个：计划在 M1 就做分布式限流或异步队列。

### D2：是否保留 MySQL + PostgreSQL 双库？（已确认：保留）

当前结论：**保留，但延迟到 M3 真正开始 RAG 时启用**。  
替代方案：M3 仍使用 MySQL，先不做向量检索；优点是部署简单，缺点是后续需要迁移知识库且 MySQL 不是当前设计的向量检索目标。

### D3：用户历史画像是否进入 PG/embedding？（已确认：进入，但需隔离）

> ✅ **2026-09-28 大宋拍板：采用本条（D3）**。落点：契约 §8.3 已改为「公共知识库严禁用户数据；用户画像另立私有空间」；契约 §8.4 的 `knowledge_chunk` 需在 **M3** 补 `owner_type` / `owner_id` 两个字段用于隔离（画像数据结构确定后一并落）。

当前结论：**进入，但不能进入公共知识空间**。必须另定：按用户隔离、删除传播、embedding 版本、敏感字段禁入清单和保留期限。建议采用“用户私有知识空间”，使用 `tenant_id/user_id` 过滤，禁止跨用户召回。

### D4：Session 是否永远以 MySQL 为事实源？（已确认：是）

推荐：**是**。这与当前接口契约一致，也避免 Redis 重启导致全量掉线或引入双写一致性问题。

#### D4 的三种实现方式

| 方案 | 请求路径 | 优点 | 代价 / 风险 |
|---|---|---|---|
| A. MySQL 直查（推荐起步） | Cookie token hash → MySQL `user_sessions` → 用户 | 语义最简单；登出/踢设备立即生效；只有一个事实源 | 每个鉴权请求都有一次 MySQL 查询，需要索引和连接池 |
| B. Redis 缓存 + MySQL 回源 | 先查 Redis，miss 再查 MySQL；写操作更新/删除缓存 | 降低高并发鉴权读压力 | 需要处理 TTL、缓存击穿、撤销传播；短时间内可能放行已登出的 Session |
| C. Redis 唯一存储 | Cookie token hash → Redis | 读写快，TTL 直观 | Redis 丢失即全员掉线；持久化、集群、故障恢复复杂；与当前 MySQL 表设计冲突 |

建议采用 **A**。如果压测证明鉴权查询成为瓶颈，再采用 B，并明确“撤销操作先写 MySQL，再删除 Redis；缓存只允许短 TTL”。不建议 C。

#### D4 推荐实现的最小约束

- Cookie 只保存随机 token；MySQL 只保存 `sha256(token)`。
- `get_current_user` 按 `token_hash + revoke_time IS NULL + expire_time > now` 查询，并通过 `user_id` 取用户。
- 登出、改密、踢设备先更新 MySQL；不依赖 Redis 删除才能生效。
- `user_sessions.token_hash` 必须唯一并有索引，`expire_time` 必须有清理索引。
- 过期会话用定时清理任务删除或归档，不能在请求链路依赖 Redis 扫描。

#### 对话最近消息的 Redis 用法

后续对话功能可以使用 Redis 保存每个会话的最近消息，但它必须是“热上下文缓存”，不是完整记录的事实源：

- 完整用户消息、Agent 输出、工具调用和 `trace_id` 持久化到 MySQL，满足审计与回放；
- Redis 只保留最近 N 条消息或最近 T 分钟消息，使用结构化 JSON，设置 TTL 和长度上限；
- 读取上下文时优先读 Redis，缓存未命中再从 MySQL 取最近记录并回填；
- 新消息先写 MySQL，成功后再写 Redis；Redis 写失败不能导致消息丢失，但要记录缓存降级；
- 删除对话或账号时先删除 MySQL 记录，再删除对应 Redis key，并提供补偿清理任务；
- Redis key 必须包含 `user_id` 和 `conversation_id`，禁止只使用客户端传来的会话名；
- Redis 不保存密码、验证码原文、完整敏感身份信息或不可恢复的唯一业务数据。

推荐键形状：`conversation:{user_id}:{conversation_id}:recent`。

### D5：缓存过期时的产品语义是什么？（已确认：标记为非实时数据）

当前结论：**过期缓存可以返回，但必须明确标记为非实时数据**。`PriceMatrix` 至少携带 `source`、`observed_at`、`expires_at`、`is_realtime`（或等价字段）；前端必须展示“数据可能已过期，以平台实时页面为准”。缓存不得伪装成当前价格。

## 4. 建议补入正式契约的最小规则

```text
当前启用：MySQL 8（业务事实源）；Session Cookie + MySQL user_sessions。
M0-M2：不依赖 Redis、PostgreSQL、pgvector；相关服务不是本地启动前置条件。
M3：PostgreSQL 16 + pgvector 仅承载公共知识、切片、embedding、检索元数据；独立连接与迁移。
M3/M5：Redis 仅用于有明确 TTL/原子计数需求的临时数据；不能替代 MySQL/PG 事实源。
对话上下文：MySQL 保存完整记录；Redis 只缓存最近消息，允许丢失，可回源重建。
禁止：跨库外键、跨库事务、把 Redis 命中当实时价格、把用户私密对话直接写入公共 embedding。
跨库流程：异步、幂等、可重试、可观测；失败不得静默丢弃。
```
