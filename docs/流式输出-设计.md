## 0. 指导原则（大宋 13:44 原话，设计的出发点）

> **聊天记录负责忠实记录发生过什么，上下文构造负责决定哪些内容值得再次交给模型。
> 两者不应该使用完全相同的过滤规则。**

这句话否定了小宋早先「统一加 completed 过滤」的说法——那把两件事混成了一件。

由它派生出**三条数据出口、三套规则**：

| 出口 | 用途 | completed | interrupted | failed | 理由 |
|---|---|---|---|---|---|
| `list_messages` | 前端展示 | 全留 | 全留 | 全留 | 忠实记录。用户有权看到「当时失败了」 |
| `messages_for_context` | 拼模型上下文 | 进 | 出 | 出 | 见下 |
| `messages_for_profile` | A6 画像输入 | 进 | **仅行为事件进，半截回答出** | 出 | 见下 |

### 为什么 interrupted 在两处待遇不同（**本设计最容易被误改的一处**）

- **上下文**：用户按下停止 = 他明确否决了这个方向。塞回上下文，模型下一轮会顺着用户已放弃的半截话继续答。**用户已用行为表态，AI 应该尊重。**
- **画像**：但「用户主动打断」本身是**高价值信号**——它说明「不是这个方向 / 说太长了 / 问错了」。这个信号要留。留的是**事件**，不是那段半截文本。

所以 A6 拿到的不是「半截内容」，而是一条形如 `（用户中断了上一轮回答）` 的**占位事件**（§4.3）。

## 1. 数据模型：新增 status 列

### 1.1 `chat_message` 加一列

```python
# app/models/chat_message.py
status: Mapped[str] = mapped_column(String(16), default="completed", nullable=False)
```

**取值只有三个**：`completed` / `interrupted` / `failed`

**语义**：

| status | 含义 | role |
|---|---|---|
| `completed` | 正常收完 | user 恒为此值；assistant 正常生成完毕 |
| `interrupted` | 用户主动取消 | assistant |
| `failed` | 模型异常且已有部分输出 | assistant |

### 1.2 三条硬约束

1. **user 消息的 status 恒为 `completed`**，不参与状态机——它请求开始就入库，没有「中断」的语义。
2. **默认值为 `completed`**，不是 nullable。旧数据迁移时全部回填 `completed`，`trim_trailing_users` 的现有行为**零回归**。
3. **不加物理外键**（沿用决策 #30 口径），不加额外索引——现有 `ix_chat_message_user_conversation` 已覆盖 `WHERE user_id=? AND conversation_id=?` 的前缀。

### 1.3 空输出的 failed 消息 —— 不落库（大宋拍板前的小宋建议，大宋未反对）

一个 token 都没收到就报错时，**不写 assistant 行**。理由：

- `content` 是 `nullable=False` 的 `Text`，空串进上下文会让模型看到一个空回复，行为不可预期
- 不落库 → 历史自然变成「连续两条 user」→ **现有 `trim_trailing_users` 自动修好**，不需要改它
- 前端从 SSE 的 `error` 事件知道失败了，不需要库里有个空消息占位
- 失败率统计将来走监控，不该靠业务表

**判定位置**：流结束时 `if not accumulated_text.strip(): 不落库`。

## 2. 数据库事务：三段式（大宋 13:44 拍板）

### 2.1 为什么必须分段

`app/dependence.py:14` 的 `get_db_session` 是 yield 依赖，**在整个响应完成后才清理**。SSE 是一个持续几十秒的响应——若用它，**一个用户在生成期间独占一个连接**。

连接池配置（`app/database/session.py:6,9`）：`pool_size=10, pool_timeout=30`

- 非流式：一次请求占连接几百毫秒，10 个绰绰有余
- 流式：**10 个并发吃满池子，第 11 个用户等 30 秒后 `pool_timeout` 报错**

**这是非流式 → 流式最容易被忽略的退化点，且单人单浏览器自测发现不了。**

### 2.2 三段边界

```
阶段① 请求准备（持连接，短，毫秒级）
    async with async_session_local() as session:
        建/查会话、拉历史、取画像、取 KeyRecord
        写 user 消息 → commit
    #← session 退出，连接归还池
         ↓
阶段② 流式生成（零连接）
    纯内存累计 assistant 文本 + httpx 流式读模型
         ↓
阶段③ 结果持久化（新 session，短）
    async with async_session_local() as session:
        写 assistant 消息 + status（有文本才写）
        touch conversation
        commit
    #← 连接归还
```

### 2.3 🔴 阶段①的关键纪律：ORM 行必须压成纯数据

**session 关闭后实例变 detached，那时再访问 `row.content` 会踩 `DetachedInstanceError`**——这是本项目 MissingGreenlet 一族的老坑，`profile_service.py:204-208` 的注释里踩过。

所以阶段①取出的一切（历史消息内容、KeyRecord、画像上下文）**必须在 session 内转成 `str` / `dict`**，阶段②③只碰纯数据。

### 2.4 `stream_model` 的签名（**大宋拍板：只负责生成**）

> 🔴 **2026-10-17 契约变更**：为支持工具调用，产出从 `AsyncIterator[str]`
> 改成 `AsyncIterator[StreamEvent]`。`call_model` 返回值也从 2 元组变成 3 元组。
> 详见 §2.6。

```python
async def stream_model(key: KeyRecord, messages: list[dict], *,
                       tools: list[dict] | None = None,
                       max_token: int | None = 6000) -> AsyncIterator[StreamEvent]
```

- **不接收 `AsyncSession`**——大宋 13:44 明确「移除 AsyncSession 参数」
- **不写库、不碰业务逻辑**——只负责把模型的流式输出逐块吐出来
- `KeyRecord` 由调用方在阶段①查好传入（大宋拍板：`call_model` 收 KeyRecord）
- **注意**：`call_model` 收到 401/403 时会调 `api_key_service.mark_invalid(record.key_id, user_id, session)` 标记 key 失效。`stream_model` 没有 session，**这个标记动作必须由调用方（阶段③）在拿到错误码后执行**——见 §5.4

### 2.6 🔴 `StreamEvent`：产出不再是裸字符串（2026-10-17 改）

**为什么必须改**：模型决定调工具时，`delta.content` 是 `null`（内容全在
`delta.tool_calls` 里）。旧契约「只 yield str」会导致整个响应**一个字都不产出**——
前端表现为「转圈半天然后失败」，**且不报错**。这是最难查的一类问题。

```python
@dataclass
class StreamEvent:
    kind: Literal["text", "tool_call"]     # 两种事件，调用方必须能区分
    text: str = ""
    tool_call: ToolCall | None = None      # kind="tool_call" 时有值

@dataclass
class ToolCall:
    id: str
    name: str
    arguments: str      # 🔴 未解析的 JSON 字符串；用 parsed_arguments() 取 dict
```

**三条硬约束**（都是 2026-10-17 实测踩出来的）：

| # | 约束 | 不这么写会怎样 |
|---|---|---|
| 1 | `arguments` 是**分片到达**的，必须**拼接不能覆盖** | 覆盖后拿到残缺 JSON，`json.loads` 炸 |
| 2 | `id` / `name` **只在首个 chunk 出现**，后续是 `None`，不能被覆盖 | 覆盖成 `None` → tool_call 没有函数名，工具节点拿不到函数名 |
| 3 | `tool_call` 事件在**流收尾时**才 yield | 中途发出去的是半截 JSON |

⚠️ **第 3 条还有一个更隐蔽的坑**：收尾代码写在 `for raw in resp.aiter_lines()` 循环**之后**，
所以 `[DONE]` 处必须 `break` **不能 `return`**——`return` 会直接退出函数，
收尾那段根本执行不到（2026-10-17 我第一版就写错了，是测试把它抓出来的）。

**破坏性变更**：`call_model` 返回值从 `tuple[str, str]` 变成
`tuple[str, str, list[ToolCall]]`。**所有解包 2 个值的调用方都要改**——
Python 不会报错（多余元素被静默丢弃），但拿到的是错的东西。

> 📌 调用点共 3 处：`chat_service.send_message`、`profile_service.refresh_profile`、
> `spec_complete_service.complete_specs`。改的时候别漏。
> ⚠️ 顺带修出一个 2026-10-16 改造的遗留 bug：`complete_specs` 还在按老签名调
> （传 `user_id` + `session=`），导致 `POST /cart/items/ai-draft` 一直是坏的。

### 2.5 🟡 连接池：本地开发**不动**，部署服务器时再调（大宋 13:52 拍板）

**实测依据（本机MySQL，2026-10-16）**：

```

wait_timeout    = 28800← 8 小时
当前已连接= 10        ← 正好等于 pool_size=10
```

**为什么本地改了也没用**：本项目是**本地 MySQL**（`localhost:3306`，AGENTS.md §「各自使用自己电脑上的 MySQL」）。两人各连各的库，**连接数互不干扰**；本地场景同时在线的就是 1–2 人，`pool_size=10` 远够不上151 这个上限。

## 3. `call_model` 改造：大宋拍板接收 KeyRecord

### 3.1 签名变更

```python
# 改前
async def call_model(user_id, messages, session: AsyncSession, *, max_token=6000) -> tuple[str, str]
# 改后
async def call_model(key: KeyRecord, messages: list[dict], *, max_token=6000) -> tuple[str, str]
```

**连带影响**：`call_model` 现在还报「未配置模型」的错（`key_for_call` 抛 `PARAM_INVALID`）。改造后这个检查上移到调用方——**每个调用点都要在阶段①先 `key_for_call`**。调用点共 3 处：

| 调用点 | 改造后怎么拿 key |
|---|---|
| `chat_service.py:64` | 阶段①查好传入 |
| `profile_service.py:238` | 已有自建 session，先 `key_for_call` 再传出 |
| `stream_model`（新） | 同上 |

### 3.2 🔴 `_log_truncation` 会静默失效（**改的时候极易漏**）

`app/services/model_call.py:26` 的 `_log_truncation()` 读 `data["usage"]["completion_tokens_details"]`。

**非流式**下这个字段在响应体里，随便读。**流式**下 `usage` 通常**只在最后一个 chunk 才出现**，且 `stream_model` 按大宋拍板「只负责生成」不碰日志。

**后果**：流式下模型输出被 `max_tokens` 截断时，**不会报错，只是日志少一行**——静默退化，最难发现。

**处理**：`stream_model` 在收到带 `usage` 的 chunk 时，把它作为最后一个 yield 值带出（或走一个 `on_usage` 回调），由阶段③打这条 warning。

## 4. Repository 拆分：**参数化是错的，拆函数才对**

### 4.1 为什么不加过滤参数（大宋 13:44 原则的直接推论）

现状：`recent_messages` 被 **2 处**共用，但它们要的东西不同——

| 当前调用方 | 位置 | 用途 |
|---|---|---|
| `chat_service.py:51` | 拼模型上下文 | 给 LLM 看 |
| `profile_service.py:209` | A6 画像输入 | 提炼长期偏好 |

**加参数的风险**：两个调用方在不同文件、不同协作者维护，迟早有人传错过滤条件，而且传错了**不会报错**——画像只是慢慢变怪。**拆成两个语义明确的函数，函数名本身就是约束。**

### 4.2 新签名

```python
# app/repository/chat_repo.py

# ① 给模型拼上下文：只认 completed，序列必须合法
async def messages_for_context(user_id, conversation_id, limit, session) -> list[dict]

# ② 给 A6 画像：completed 进；interrupted 只留事件占位；failed 出
async def messages_for_profile(user_id, conversation_id, limit, session) -> list[dict]

# ③ 给前端展示：全留，不变，只加 status 字段透出
async def list_messages(user_id, conversation_id, limit, session) -> list[ChatMessage]
```

**返回 `list[dict]` 而不是 ORM 实体**——提前压成纯数据，杜绝 detached（§2.3）。

**每条 dict 的形状**：`{"role": str, "content": str, "model": str | None}`

### 4.3 interrupted 的事件占位

`messages_for_profile` 里，interrupted 消息**不是丢弃，也不是原文照传**，而是替换成固定文案：

```python
_INTERRUPT_EVENT = "（用户中断了上一轮回答）"
```

理由：A6 要知道「用户主动喊停了」，但**绝不能**看到那段被否决的半截内容——否则画像会从用户已放弃的文本里提炼偏好。

### 4.4 🔴 `trim_trailing_users` 的前提破了，必须回归测试

`chat_repo.py:29` 的 `trim_trailing_users`，注释写得很清楚：

> 由于采用 user 信息先落库，如果出现模型调用失败，会导致连续两次 user 信息，部分模型不支持连续两次 user 信息

它**靠「assistant 从不落库」这个前提**工作。

**新方案下前提变了**：failed 消息会落库、interrupted 消息会落库。虽然 §1.3 让空 failed 不落库，但**有半截文本的 failed 依然落库**，且插在序列中间。

**好消息**：因为 `messages_for_context` 只认 completed，**失败/中断的 assistant 在进入上下文前已被过滤掉**，序列回到「user 失败 → 只有 user 落库」的老形态，`trim_trailing_users` 的前提**重新成立**。

**但这依赖「过滤发生在 trim 之前」这个顺序**，属于隐式契约 → **必须写回归测试锁住**（§7）。

## 5. SSE 协议设计

### 5.1 端点形态：新开 `/chat/stream`，保留 `/chat/message`

**理由**（小宋建议，大宋未反对）：

- 旧端点 + `postman/` 里的 yaml 保留 = 零成本后路
- 真出问题（如流式在某些代理下被缓冲）可一把切回，无需发版
- `/chat/message` 继续服务非流式场景与外部脚本

### 5.2 中间件约束（实测确认，**不需要改**）

| 组件 | 位置 | 对 SSE 的影响 | 结论 |
|---|---|---|---|
| `TraceMiddleware` | `app/core/middleware.py:29` | 只在 `http.response.start` 插 header，`finally` 里打日志；**不缓冲 body** | ✅ 可用 |
| 全局异常处理器 | `app/core/errors.py:57-86` | 返回 `JSONResponse` | ⚠️ **流开始后抛异常已无法改状态码**，见 §5.4 |
| `require_same_origin_write` | `app/dependence.py:52` | 查 `X-Requested-With` header | ✅ 前端带上即可 |
| `_TIMEOUT` | `model_call.py:17` | `httpx.Timeout(35.0, connect=8.0)` 是**总超时** | ⚠️ **必须为流式单独设**，见 §5.3 |

### 5.3 🔴 流式必须独立设 timeout（**不这么写会怎样**）

`httpx.Timeout(35.0)` 在**非流式**下是「整个请求 35 秒内完成」。

**流式下这个语义就错了**：模型生成 6000 token 可能远超 35 秒（普通模型 30–60 token/s → 100–200 秒）。若沿用 35 秒，**所有长回答都会在 35 秒被强行掐断**，且因为截断发生得很自然，**表现为「回答说到一半停了」，不报错**。

**处理**：`stream_model` 用独立 timeout——`connect=8.0` 保留（连不上要快速失败），`read=None`（不设读超时，等多久都行），或给一个大值（如 300s）。

> 另注：`app/core/http_client.py` 的共享客户端 `max_connections=100`，流式是长连接占用，**并发数上限要按这个算**。

### 5.4 错误处理的分岔（大宋拍板「状态明确区分」的落地）

**关键约束**：SSE 一旦发出 `http.response.start`，HTTP 状态码就锁死 200 了。之后出错**不能再用 `JSONResponse` 改成 500**（全局异常处理器做不到）。

所以必须**在流内用事件表达错误**：

| 时机 | 处理 |
|---|---|
| 阶段①出错（取 key/建会话失败） | 走 `BizError` → 全局处理器 → 正常 JSON 错误响应 + 正确状态码。**流还没开始** |
| 阶段②出错（模型 401/欠费/异常） | 已在流内 → 发 `error` 事件 → 阶段③按 §1/§2 落 `failed` → 关闭流 |

**事件协议**：

```
event: meta      data: {"conversation_id": 123, "model": "deepseek-chat"}
event: agent     data: {"agent": "A4", "label": "对比同类参数", "phase": "start"}

event: delta     data: {"text": "根据"}
event: delta     data: {"text": "你的"}
...

event: done      data: {"status": "completed", "message_id": 456}
event: done      data: {"status": "interrupted"}
event: done      data: {"status": "failed", "error": "模型服务已欠费，请前往对应平台充值后重试"}
```

| 事件 | 何时发 | 载荷 | 前端动作 |
|---|---|---|---|
| `meta` | 阶段①结束**立刻**发，**先于任何文本** | `conversation_id` + `model` | 立刻拿到会话 id，草稿标题转正（**流式最大的体验增益**——不用等模型答完） |
| `agent` | 子 agent 调用开始 / 结束 | `agent` + `label` + `phase` | 折叠成一行「正在查商品参数…」（**详见 §5.7**） |
| `delta` | 每收到一块模型文本 | `text` | 追加渲染到气泡 |
| `done` | 流收尾，**最后一次** | `status` + `message_id` | 气泡从「生成中」转正，回填状态角标 |
| `error` | 模型报错 / 欠费 / key 失效 | 用户可读中文 | 显示红色错误行（**不能只存在于流里**） |

- `error` 信息**由后端翻译成用户可读中文**，`str(exc)` 透传（沿用 `chat_service` 现有口径：不暴露 key / base_url）
- 前端收到 `error` / `done(failed)` 时，**同时在输入框上方显示 `errorMessage`**——不能让失败只存在于流里
- **`done` 必须带 status** 而不只是当结束标记：assistant 有三种状态，前端刷新后要显示「已停止 / 生成失败」角标，得知道落库时到底是什么状态

### 5.7 🟡 `agent` 事件：**只显示「在调用」，不显示子 agent 的输出**（大宋 13:52 拍板）

**大宋决策**：将来接入子 agent（A2′ 商品情报 / A4 对比 / A5 推荐）时，**前端不显示子 agent 的输出内容，只显示它正在被调用**。

**为什么第一版就要留这个事件**：现协议是**单层**的（一请求→一模型→一串delta）。将来 A1 编排子 agent 后变成**树状**：

```
A1（主管）
├── A2′ 商品情报
├── A4 对比
└── A5 推荐
```

若协议现在不留门，后面加就得**同时改后端和前端渲染**。留门的成本几乎为零。

**事件形态**：

```
event: agent  data: {"agent": "A4", "label": "对比同类参数", "phase": "start"}
event: agent  data: {"agent": "A4", "phase": "end"}
```

- **不带任何文本内容**——子 agent 的 delta **一律不发前端**
- 前端渲染成**折叠的一行**「正在查商品参数…」，`phase:end` 时收起（或变成一个淡标记）
- **不进 `chat_message` 表**——它是过程事件不是对话消息；且 `messages_for_context` / `messages_for_profile` 都不该看到它

**🔴 关键区分**：`agent` 事件 ≠ `delta` 事件。第一版没有子 agent，但 **`meta` 之后的第一个 `delta` 之前有个空窗**（模型读完 prompt 才开始吐字，通常 1–3 秒）。这段时间屏幕上不能白着——**「正在思考…」这个占位就复用 `agent` 事件的形态**（或 `meta` 后前端本地起一个 loading，不必等后端）。

### 5.5 客户端取消的三种情形（§6 状态机的输入）

| 情形 | 检测方式 | 落库 |
|---|---|---|
| 用户点「停止」按钮 | 前端 `AbortController.abort()` | `interrupted` |
| 用户切路由 / 关页面 | 同上（组件 `onBeforeUnmount` 里 abort） | `interrupted` |
| 网络抖动断连 | 后端感知到 `GeneratorExit` / `CancelledError` | `interrupted` |

**注意区分「用户取消」与「模型失败」**：前者 `interrupted`，后者 `failed`。异常类型不同，别混。

### 5.6 空输出的处理路径

模型流式过程中一个 delta 都没来就报错 → `accumulated_text` 为空 → **不落库**（§1.3）→ 只发 `done{status:"failed"}` → 前端显示错误 + 会话里只有 user 那条。

### 5.8 客户端约束（大宋 13:59 拍板，**硬约束**）

**接口**：`POST /chat/stream`

1. **必须**用 `fetch` 发起，通过 `ReadableStream` 消费 SSE 数据
2. 请求**必须**携带 `X-Requested-With: price-agent`——`require_same_origin_write`（`dependence.py:52`）只认这一个头
3. 请求体用 JSON，按接口约定传聊天内容与参数
4. 客户端用 `AbortController` 实现用户主动停止
5. 客户端**必须**处理：非2xx HTTP 响应、流读取异常、连接中断、服务端发送的终止事件
6. **禁止**使用原生 `EventSource`——它不支持自定义请求头与 POST 请求体，不符合本接口约定

**为什么第 6 条是硬约束**（不是偏好）：`EventSource` 规范上只支持 GET、且**不允许自定义 header**。第 2 条的同源校验靠自定义头，所以 `EventSource` 用不了。这是 `require_same_origin_write` 这个既有设计带来的必然结果。

### 5.9 🔴 客户端中止 ≠ 服务端已落库（大宋 13:59 补充）

> **客户端中止请求不代表服务端已经完成取消及结果持久化。服务端必须正确处理请求取消，并按最终生成状态保存消息。**

这条把 `interrupted` 的语义钉死了，它是**异步落库最容易漏的一环**：

```
前端 abort()  ──►  HTTP 连接断开
                │
                ▼
        服务端生成器收到 GeneratorExit / CancelledError
                │← ⚠️ 这一步是【异步】的，不是 abort() 返回时就算完
                ▼
        必须：走 catch/finally → 用新 session 落库 interrupted → 关闭流
```

**具体要防的两个错**：

| 错法 | 后果 |
|---|---|
| 前端 `abort()` 后**立刻**恢复输入框、允许再发一条 | 用户连发两条，但第一条还没落库 → **历史里 assistant 缺失**，上下文断裂 |
| 生成器抛 `GeneratorExit` 后**直接 raise 不落库** | 同上，且前端已显示「已停止」，刷新后那条消息消失 |

**对应的两个硬要求**：

1. **前端 `stopping` 态必须等服务端 `done` 才回 `idle`**（§6.1已写）——不能 abort 就解锁
2. **服务端在 `GeneratorExit` / `CancelledError` 分支里必须落库**，不能只置状态

**验收方法**：发一条长回复 → 生成中点停止 → 立刻刷新页面 → **那条 assistant 消息必须还在，且状态角标是「已停止」**。若消失，就是漏了落库。

## 6. 前端渲染状态机

现有 `ChatView.vue:155-194` 的 `send()` 是 `await sendChatMessage(...)` 一次性 push，**无任何流式代码**。全项目搜不到 `EventSource` / `getReader` / `TextDecoder`。

### 6.1 发送态四值

```js
const sendState = ref('idle')  // idle | streaming | stopping | error
```

- `streaming`：输入框禁用，显示「停止」按钮
- `stopping`：已 abort，等后端确认 `done`，按钮转 loading（**不能立即恢复输入框**——后端还在写库）
- 收到 `done` 后回到 `idle`

### 6.2 乐观消息的两阶段

```
点发送 → 立即 push user 消息（现状已有）
      → push 空 assistant 占位 { text: '', status: 'streaming' }
      → 逐个 delta 追加到该占位的 text
      → done 事件到达 → 回填 status + message_id
      → error 事件到达 → 回填 status='failed' + 显示错误行
```

**关键**：assistant 占位**必须在发请求前就 push**，否则第一个 delta 到达时没有容器可追加。

### 6.3 刷新后角标还在（依赖 schema 扩展）

现状 `MessageOutSchema` 只返回 `role/content/model/create_time`，**没有 status**——历史消息加载时看不到状态，刷新后「已停止 / 生成失败」角标会消失。

**必须扩 schema**：

```python
class MessageOutSchema(BaseModel):
    id: int
    role: str
    content: str
    model: str | None
    status: str          # ← 新增
    create_time: datetime
```

### 6.4 历史消息仍显示非 completed 消息

`messages_for_context` 的过滤**只作用于模型上下文**。前端读的是 `list_messages`，**全留**。用户刷新后仍能看到「当时那条失败了」——这是 §0 原则的「忠实记录」。

### 6.5 🔴 「正在思考」占位不能等后端（**第一版就有**）

`meta` 发完之后、第一个 `delta` 到达之前，有 **1–3 秒空窗**（模型要先读完 prompt）。这段时间屏幕上不能白着。

**前端在 push 完 assistant 占位气泡后，本地立即起loading 态**，不等后端：

```
点发送 → push user 消息
      → push assistant 占位 { text:'', status:'streaming' }← 渲染成「正在思考…」
      → fetch + getReader()
      → 第一个 delta 到达 → 占位转正文，loading 消失
      → done / error → 回填 status
```

**注意**：`agent` 事件（§5.7）将来承担「正在调用子 agent」的提示，但**第一版没有子 agent**，那个空窗只能靠前端本地起loading。两者不要混实现。
